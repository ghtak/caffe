# 토큰 인증 정책과 결정 근거

## 목적

여러 기기에서 독립적으로 로그인할 수 있도록 JWT 액세스 토큰과 로그인별 리프레시 토큰을 사용한다. 일상적인 사용의 편의와 탈취 시 피해 기간 제한 사이의 균형을 선택한다. (확인)

## 현재 선택

- **로그인별 리프레시 토큰 유지:** 로그인마다 별도 토큰을 발급하고, 갱신 시 같은 토큰을 유지한다. 한 기기의 로그아웃이 다른 기기의 로그인에 영향을 주지 않으며, 토큰 교체에 따른 동시 요청·응답 유실 처리 부담을 줄인다. 멀티 로그인 자체는 토큰 교체 방식으로도 구현할 수 있다. (확인·추론)
- **절대 만료:** 리프레시 토큰은 활동 중에도 최초 발급으로부터 30일을 넘겨 사용할 수 없다. 평소에는 일반 만료를 연장해 재로그인 빈도를 줄이되, 장기간 재인증 없이 유지되거나 탈취된 토큰의 사용 가능 기간에 상한을 둔다. (확인·추론)
- **짧은 액세스 토큰 수명:** 액세스 토큰은 15분 후 만료된다. 서버 조회 없이 JWT를 검증하는 비용상 이점을 유지하면서 탈취 또는 권한 변경의 영향 기간을 제한한다. (확인·추론)

## 감수하는 보안 한계

- 동일 리프레시 토큰을 재사용하므로 정상 사용자와 탈취자의 사용을 구분하거나 재사용으로 탈취를 감지할 수 없다. 절대 만료는 피해 가능 기간을 제한할 뿐 탈취를 방지하지 않는다. (추론)
- 로그아웃은 해당 리프레시 토큰만 취소한다. 이미 발급된 JWT는 별도 서버 측 취소 확인이 없으므로 만료 전까지 유효할 수 있다. 다른 로그인도 유지된다. (확인·추론)
- JWT라는 형식 자체가 탈취 대응을 불가능하게 만드는 것은 아니다. 서버 측 상태 확인, 토큰 교체 또는 발급 대상에 토큰을 묶는 방식으로 위험을 줄일 수 있지만, 상태 관리와 운영 복잡도가 늘어난다. (추론)
- OAuth 공개 클라이언트의 리프레시 토큰에 관한 [RFC 9700 §4.14](https://datatracker.ietf.org/doc/html/rfc9700#section-4.14)는 재사용 탐지를 위해 매번 교체하거나 발급 대상에 토큰을 묶도록 요구한다. 이 서비스의 자체 세션 정책에 해당 요구를 그대로 적용하는 것은 아니며, 현재 선택은 그보다 낮은 재사용 탐지 수준을 감수한다. (확인·추론)

## 필요 시 보완 방향

- **전체 로그인 취소:** 사용자가 탈취를 의심할 때 모든 리프레시 토큰을 취소하는 기능을 추가할 수 있다. 이후 새 액세스 토큰 발급을 막지만 이미 발급된 JWT를 즉시 무효화하지는 않는다. (추론)
- **민감 경로의 세션 기반 처리:** 보안 요구가 높은 경로에는 필요 시 서버 측 세션 기반 처리를 도입해 인증 상태와 취소를 관리하는 방안을 검토한다. 필요한 경우 재인증이나 추가 인증을 함께 적용한다. (추론)
- 위 기능은 현재 구현이나 확정된 요구사항이 아니다. 민감 기능의 범위, 인증 수단과 취소의 즉시성 요구가 생기면 구체적으로 결정한다. (확인)
