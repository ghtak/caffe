# Rust 구현 세부 지침

## 1. 사전 파악 기준

- 변경 대상과 인접한 기존 슬라이스 및 테스트를 읽어 레이어 구조, 오류 변환 방식, 트랜잭션·핸들 전달 관례, 호출 패턴, 코드 밀도를 확인한다.

---

## 2. Phase 1. 계약 및 골격 설계 기준

- **골격 작성:** 엔터티, 오류, 입출력 DTO/도메인 타입, 트레이트 및 함수 시그니처를 가독성 우선으로 작성한다.
- **본문 스텁 처리:** 단순 생성자·접근자를 제외한 신규 함수 본문은 `todo!("주요 계약 조건과 제약 사항")` 형태로 1~2문장 이내로 작성한다. 비즈니스 로직, DB 쿼리, 외부 API 호출은 작성하지 않는다.
- **정적 확인:** `cargo check` 및 모듈 가시성(`pub`)만 확인하고, 테스트는 작성하지 않는다.

---

## 3. Phase 2. 상세 구현 및 검증 기준

### 3-1. 구현 밀도 원칙
- 외부 입력 경계에서만 검증·변환하고, 내부 모듈은 도메인 타입과 표준 크레이트의 불변 조건을 신뢰한다.
- 핵심 로직이 최상위 흐름에서 직선적으로 읽히도록 작성하고, 경계 변환 외에는 `?`로 즉시 위임하며 불필요한 중간 열거형이나 1회용 래퍼를 만들지 않는다.
- 테스트는 [Rust 테스트 지침](../../test-guide/references/rust.md)을 따라 도메인 계약과 실제 실패·보안 경계만 간결하게 검증한다.

### 3-2. 포맷 및 정적 검증
- 구현 후 `cargo +nightly fmt --all --`로 포맷팅한다.
- 변경 규모와 위험도에 맞춰 `cargo test`, `cargo clippy` 등을 실행하고 통과를 확인한다.

### 3-3. 자체 점검 체크리스트
1. 각 구성 요소가 맡은 책임과 계층 경계를 지키는가?
2. 신뢰 경계 바깥의 입력만 검증하고, 내부 불변 조건이나 표준 크레이트 스펙을 중복 검증하지 않았는가?
3. 불필요한 중간 열거형이나 1회용 래퍼 없이 핵심 흐름이 직선적으로 드러나는가?

## 4. Phase 3 리뷰 위임 매핑

- **적용 스킬:** [rust-review](../../rust-review/SKILL.md) (첫 메시지에 `$rust-review` 적용)
- **전달 내용:** 변경 목적·계약, 기준 슬라이스(비교 기준), 검토 대상 파일·모듈 목록
