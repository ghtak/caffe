# 프런트엔드 구현 세부 지침

## 1. 사전 파악 기준

- 작업 전 [프런트엔드 구조 가이드](../../../../docs/agents/frontend_structure.md)를 읽고 프로젝트 구조, 의존성 경계, 상태 관리, 스타일링 기준을 적용한다.
- 인접 `feature` 슬라이스, 라우트, 공용 UI 컴포넌트(`shared`), 기존 테스트를 확인해 데이터 패칭 관례, 스타일링 패턴, 코드 밀도를 파악한다.

---

## 2. Phase 1. 화면·상태 계약 및 정적 시안 기준

- **설계 범위:** 화면 목적과 사용자 흐름을 기준으로 필요한 라우트, 레이아웃, 컴포넌트와 각 구성 요소의 책임·상태 소유권을 정한다.
- **계약 정리:** 입력과 출력, URL 파라미터, API 계약, 로딩·빈 결과·오류 상태, 사용자 동작 및 접근성 요구사항을 정리한다.
- **정적 시안:** 의존성 경계를 존중해 타입·인터페이스와 컴포넌트 골격을 작성하고, 화면 구성과 시각적 방향을 확인할 수 있는 정적 시안을 구성한다(필요 시 대표 상태·예시 데이터 표시).
- **구현 제한:** 실제 비즈니스 로직이나 API 연동은 구현하지 않으며, 예시 데이터와 미동작 요소는 시안 리뷰 시 명확히 알린다.
- **정적 확인:** 타입 검사와 import 경계만 확인하고, 테스트는 작성하지 않는다.

---

## 3. Phase 2. 상세 구현 및 검증 기준

### 3-1. 구현 밀도 원칙
- 서버 상태, 전역 UI 상태, URL 상태, 로컬 입력 상태의 소유권을 명확히 나누고 불필요한 파생 상태·중복 동기화를 만들지 않는다.
- 외부 API 응답과 URL·폼 입력은 경계에서 한 번만 검증·변환하고, 내부 컴포넌트는 확정된 타입을 신뢰한다.
- 테스트 추가·수정 시 [프런트엔드 테스트 지침](../../test-guide/references/frontend.md)을 따른다.

### 3-2. 테스트 및 화면 확인
- 사용자에게 중요한 동작과 실제 발생 가능한 로딩·빈 결과·실패 상황을 간결하게 검증한다.
- 프로젝트의 타입 검사·린트·빌드·테스트 명령을 실행해 통과를 확인한다.
- UI 변경은 가능한 환경에서 실제 화면을 확인하고, 확인하지 못한 화면이나 상태는 검증 결과에 명시한다.

### 3-3. 자체 점검 체크리스트
1. 각 화면과 컴포넌트가 맡은 책임과 상태 소유권을 지키며 불필요한 상태 복제가 없는가?
2. 라우트·feature·shared 사이의 의존성이 프로젝트 경계를 지키는가?
3. 외부 데이터와 사용자 입력을 경계에서 검증·변환하고 내부 중복 방어를 배제했는가?
4. 로딩·빈 결과·오류 상태, 사용자 동작 및 기본 접근성(시맨틱 마크업·키보드 조작)이 계약에 맞게 처리되는가?
