# 코드 구현 워크플로우

## 1. 진입 기준

- Phase 1 시작 (기본값): 상위 스펙이나 시각 시안 없이 신규 기능·화면, 도메인 모델링, 사용자 흐름, 공개 계약을 처음 설계·구현할 때 적용.
- Phase 2 즉시 시작:
  - `macro-spec` 등 상위 설계 문서에서 도메인·화면 흐름과 API 계약이 이미 확정된 개별 태스크 구현
  - 범위가 명확한 단순 버그 수정 또는 내부 리팩토링
- 우선순위: 사용자의 명시적 지시가 기본 진입 기준보다 우선.

---

## 2. 작업 파이프라인

### 사전 단계. 스택 지침 로드 및 기존 코드·상태 파악 (공통)

Phase 1과 Phase 2 중 어디로 진입하든 코드 작성 전에 반드시 먼저 수행한다.

1. 스택별 참조 문서 로드: 작업 대상에 해당하는 지침을 먼저 읽고 기준을 적용한다(풀스택 작업이면 둘 다 로드).
   - Rust 백엔드·시스템: [Rust 구현 지침](references/rust.md)
   - 프런트엔드 UI: [프런트엔드 구현 지침](references/frontend.md)
2. 기존 코드·테스트 파악: 코드 베이스 기반 슬라이스, 라우트·공용 모듈, 기존 테스트를 읽어 구조, 오류·상태 처리 관례, 구현 계약, 코드 밀도를 파악한다.
3. 작업 상태 초기화 및 계약 기록: [일회용 작업 상태 관리](../todo-state/SKILL.md)에 따라 `.agent/.state/todo.md`를 복구하거나 최초 생성한다.
   - 초기 계약 기록: Phase 2 직접 진입 시에는 사용자 요청이나 상위 설계에서 확정된 핵심 계약·범위를 `## 계약·가정`에 기록한다(Phase 1 진입 시에는 초안을 기록한 뒤 계약 승인 후 갱신).
   - 풀스택 정렬 기준: 풀스택 작업은 사용자가 UI 프로토타이핑 선행을 명시하지 않는 한 `[BE]` 항목을 먼저 배치하고 `[FE]` 항목을 뒤에 배치한다.

---

### Phase 1. 계약·골격 설계 및 정적 시안 (계약 승인 게이트)

1. 골격·시안 작성: 스택별 지침에 따라 계약 골격(엔터티, 입출력·상태 타입, 인터페이스 시그니처, 정적 UI 시안)을 작성한다.
   - 풀스택 동시 확정: 풀스택 작업에서는 화면에 필요한 데이터 필드가 API 계약에서 누락되지 않도록 BE API 계약(입출력 타입)과 FE 정적 시안을 한 번에 함께 작성해 동시 승인받는다.
2. 구현 제한: 실제 비즈니스 로직, DB 쿼리, 외부 API 연동을 구현하지 않는다. 기존 계약이 불명확하면 확인된 사실과 가정을 구분해 명시한다.
3. 정적 확인: 스택별 Phase 1 검증 명령(컴파일·타입 검사·import 경계)만 확인한다. 이 단계에서는 테스트를 작성하지 않는다.
4. 계약 승인 요청: 골격·주요 계약·시안을 사용자에게 보고하고 계약 승인을 요청한다. 계약 승인 전 상세 구현(Phase 2) 진입 금지.

---

### Phase 2. 상세 구현 및 도구 검증

#### 2-1. 로직·화면 구현 및 테스트
- 승인된 계약·시안에 따라 실제 로직, 상태 전이, 데이터 연동을 구현한다(Phase 1 생략 시 요청 범위 즉시 구현).
- 풀스택 실행 순서 (`BE → FE`):
  - 사용자가 UI 선행을 명시한 경우를 제외하고 `[BE]` 구현 및 도구 검증(`2-2`)을 완료한 뒤 `[FE]`를 진행한다(환경 제약으로 BE 검증이 막힌 경우 해당 검증 항목을 `.agent/.state/todo.md`에 미완료(`[ ]`, 사유 기록)로 유지한 채 FE 진행만 허용한다).
  - 역행 복구 경로: `[FE]` 구현 중 API 계약 누락·변경이 필요하면 `영향 확인 → 필요한 계약 승인 → [BE] 수정 및 관련 검증 → [FE] 재개` 순으로 처리한다.
- 이미 승인된 계약은 재승인 없이 진행하되, 외부 API 계약이나 공유 타입 변경이 필요하면 영향과 대안을 먼저 제시하고 확인받는다.
- 공통 구현 밀도 원칙:
  - 외부 입력(API 요청·응답, URL, 폼 입력)은 신뢰 경계에서 한 번만 검증·변환하고, 내부 모듈은 확정된 도메인·컴포넌트 타입의 불변 조건을 신뢰한다.
  - 핵심 흐름이 직선적으로 읽히도록 작성하며, 불필요한 중간 래퍼나 중복 상태 동기화를 만들지 않는다.
  - 기준 코드의 구조와 코드 밀도를 따른다.
- 테스트 추가·수정 시 [test-guide](../test-guide/SKILL.md)와 스택별 테스트 지침을 따른다.

#### 2-2. 검증 및 계약 일치 확인 (Phase 2 완료 기준)
- 스택별 지침에 명시된 포맷터, 정적 분석(타입·린트·클리피), 테스트 및 화면 확인 절차를 실행하고 통과를 확인한다.
- 정성적 코드 품질 평가는 Phase 3 리뷰에 위임하되, 승인된 계약과 요청 범위가 누락 없이 구현되었는지만 확인한 뒤 `.agent/.state/todo.md`에 1줄 근거로 기록한다.
- 환경 제약으로 보류된 검증 항목이 있는 경우, 해당 검증이 실제로 통과하거나 사용자가 검증 제외를 명시적으로 결정한 경우에만 Phase 2 완료로 처리한다.
---

### Phase 3. 코드 리뷰

- 실행 조건: 사용자가 리뷰를 요청한 경우에만 실행(건너뛰기 요청 시 생략, 목록에는 사유 표시).
- 현재 세션 리뷰: 일반적인 리뷰 요청에는 구현 에이전트가 비교 기준과 검토 범위를 정하고 [dev-review](../dev-review/SKILL.md)를 직접 적용한다. 결과 상단에 `구현자 자체 리뷰`임을 명시하고 독립 리뷰로 간주하지 않는다.
- 독립 리뷰: 변경 규모나 권한·데이터·공개 계약 등 영향이 크면 독립 리뷰를 권고한다. 독립 리뷰는 동일 워크트리에서 새 세션을 열어 `$dev-review`로 실행하며, 새 세션은 `.agent/.state/todo.md`를 읽기 전용으로 참조한다.
- 리뷰 판정 및 후속 동작: 판정은 `dev-review`의 `통과` / `수정 필요` / `판정 보류`를 그대로 따른다. 리뷰 중 검토 대상을 직접 수정하지 않는다.
  - 리뷰만 요청된 경우: 판정과 근거를 보고하고 종료한다(임의 수정 금지).
  - 수정까지 위임·승인된 경우: `.agent/.state/todo.md`의 해당 항목을 `재진행 중`으로 되돌린 뒤 `수정 → 관련 검증 → 필요한 재리뷰` 순으로 진행한다.
  - 판정 보류 시: 부족한 검증 근거와 필요한 후속 조치를 기록하고 사용자 확인을 요청한다.

---

### Phase 4. 커밋

- 실행 조건: 사용자가 커밋을 요청한 경우에만 [commit](../commit/SKILL.md) 스킬 적용(목록에는 표시).
- 직접 처리: 구현 에이전트가 작업 목적과 포함·제외할 변경, 기존 staged 변경을 확인하고 `commit` 스킬에 따라 직접 커밋한다.
- 결과 보고: 커밋 해시·메시지·남은 변경을 보고하고 `.agent/.state/todo.md`를 갱신한다. 범위 확인이나 권한·검증 실패로 중단되면 사유와 현재 상태를 보고한다.

---

## 3. 단계 전환 및 종료 프로토콜

- 단계 전환 구분: `계약 승인`(Phase 1→2), `리뷰 통과`(Phase 3 완료), `커밋 허용`(Phase 4 실행)은 각각 해당 단계만 전환하며 전체 작업을 종료하지 않는다.
- 상태 출력: 모든 응답의 상태 표기 및 출력 형식은 [일회용 작업 상태 관리](../todo-state/SKILL.md)의 응답 출력 규칙을 따른다.

| 사용자 요청 | 상태 처리 및 개발 모드 여부 |
| --- | --- |
| 완료 보고 요청 | 현재 결과와 미완료 항목만 보고. `작업 완료` 체크, 상태 파일 삭제 및 모드 종료 금지 |
| 전체 작업 완료 확정 | 사용자가 전체 작업 완료를 명시적으로 확정한 경우에만 `작업 완료` 체크, `.agent/.state/todo.md` 삭제 및 개발 모드 종료 |
| 작업 종료(중단) 선언 | 미완료 항목과 중단 사유 기록 후 `작업 완료`(종료 의미) 체크, `.agent/.state/todo.md` 삭제 및 개발 모드 종료 |

보고/종료 시 출력 템플릿:

```text
✅ 작업 요약
   * 구현 목적, 핵심 변경 사항과 검증 결과
   * 주요 설계·로직 결정 사항
📌 작업 목록
   * [x] 완료 항목 — 근거
   * [ ] 미완료 항목 — 현재 상태와 사유
```
