# 코드 구현 워크플로우

## 1. 진입 기준

- **Phase 1 시작 (기본값):** 상위 스펙이나 시각 시안 없이 신규 기능·화면, 도메인 모델링, 사용자 흐름, 공개 계약을 처음 설계·구현할 때 적용.
- **Phase 2 즉시 시작:**
  - `macro-spec` 등 상위 설계 문서에서 도메인·화면 흐름과 API 계약이 이미 확정된 개별 태스크 구현
  - 범위가 명확한 단순 버그 수정 또는 내부 리팩토링
- **우선순위:** 사용자의 명시적 지시가 기본 진입 기준보다 우선.

---

## 2. 작업 파이프라인

### 사전 단계. 스택 지침 로드 및 기존 코드 파악 (공통)

Phase 1과 Phase 2 중 어디로 진입하든 코드 작성 전에 반드시 먼저 수행한다.

1. **스택별 참조 문서 로드:** 작업 대상에 해당하는 지침을 먼저 읽고 기준을 적용한다(풀스택 작업이면 둘 다 로드).
   - Rust 백엔드·시스템: [Rust 구현 지침](references/rust.md)
   - 프런트엔드 UI: [프런트엔드 구현 지침](references/frontend.md)
2. **기존 코드·테스트 파악:** 변경 대상과 인접한 기준 슬라이스, 라우트·공용 모듈, 기존 테스트를 읽어 구조, 오류·상태 처리 관례, 구현 계약, 코드 밀도를 파악한다.
3. **작업 목록 초기화:** 파악한 구조를 바탕으로 전체 작업 단위를 분할해 최초 Todo 목록을 생성한다.

---

### Phase 1. 계약·골격 설계 및 정적 시안 (승인 게이트)

1. **골격·시안 작성:** 스택별 지침에 따라 계약 골격(엔터티, 입출력·상태 타입, 인터페이스 시그니처, 정적 UI 시안)을 작성한다.
2. **구현 제한:** 실제 비즈니스 로직, DB 쿼리, 외부 API 연동을 구현하지 않는다. 기존 계약이 불명확하면 확인된 사실과 가정을 구분해 명시한다.
3. **정적 확인:** 스택별 Phase 1 검증 명령(컴파일·타입 검사·import 경계)만 확인한다. **이 단계에서는 테스트를 작성하지 않는다.**
4. **승인 요청:** 골격·주요 계약·시안을 사용자에게 보고하고 리뷰를 요청한다. **승인 전 상세 구현(Phase 2) 진입 금지.**

---

### Phase 2. 상세 구현 및 자체 검증

#### 2-1. 로직·화면 구현 및 테스트
- 승인된 계약·시안에 따라 실제 로직, 상태 전이, 데이터 연동을 구현한다(Phase 1 생략 시 요청 범위 즉시 구현).
- 이미 승인된 계약은 재승인 없이 진행하되, 외부 API 계약이나 공유 타입 변경이 필요하면 영향과 대안을 먼저 제시하고 확인받는다.
- **공통 구현 밀도 원칙:**
  - 외부 입력(API 요청·응답, URL, 폼 입력)은 신뢰 경계에서 한 번만 검증·변환하고, 내부 모듈은 확정된 도메인·컴포넌트 타입의 불변 조건을 신뢰한다.
  - 핵심 흐름이 직선적으로 읽히도록 작성하며, 불필요한 중간 래퍼나 중복 상태 동기화를 만들지 않는다.
  - 기존 슬라이스(기준 코드)의 구조와 코드 밀도를 따른다.
- 테스트 추가·수정 시 [test-guide](../test-guide/SKILL.md)와 스택별 테스트 지침을 따른다.

#### 2-2. 포맷·정적 분석 및 동작 검증
- 스택별 지침에 명시된 포맷터, 정적 분석(타입·린트·클리피), 테스트 및 화면 확인 절차를 실행하고 통과를 확인한다.

#### 2-3. 자체 점검
구현 완료 후 스택별 자체 점검 체크리스트를 기준으로 변경 코드를 검증하고, 어긋난 부분이 있으면 즉시 단순화한다.

---

### Phase 3. 코드 리뷰 (위임 게이트)

- **실행 조건:** 사용자가 리뷰를 요청한 경우에만 실행(건너뛰기 요청 시 생략, 목록에는 사유 표시). 구현자 자체 점검은 Phase 2 완료 근거로만 사용.
- **위임 규칙:** 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차) 사용(모델 키: `review`). 스택별 지침에 지정된 리뷰 스킬(`$dev-review`)을 첫 메시지에 적용하고, 변경 목적·계약, 비교 기준, 검토 대상을 전달한다(풀스택 변경 시 스택별로 분리 위임). 리뷰 중 검토 대상 수정 금지.
- **예외 처리:** 모델 설정이 유효하지 않거나 위임 또는 결과 확인이 불가능하면 사유를 보고하고 리뷰를 미완료 상태로 유지.
- **결과 확인 및 종료:**
  - 서브에이전트로부터 각 리뷰 스킬의 출력 양식에 따른 보고를 받아 검토 범위와 근거를 확인한 뒤 사용자에게 전달.
  - 결함이나 정적 검사 실패를 근거와 함께 보고했다면 리뷰 결과로 처리. `수정 필요` 판정도 결과 확인 후 터미널 정리.
  - 범위 확인이나 권한 승인 등 사용자 개입 후 이어갈 작업이 있으면 터미널 유지.

---

### Phase 4. 커밋 (위임 게이트)

- **실행 조건:** 사용자가 커밋을 요청한 경우에만 [commit](../commit/SKILL.md) 스킬 적용(목록에는 표시).
- **범위 정리 및 위임:** 작업 목적, 포함·제외할 변경, 기존 staged 변경 처리 범위를 정리. 범위를 명확히 전달할 수 있으면 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차)로 위임(모델 키: `commit`, 첫 메시지에 `$commit` 적용과 실제 커밋 요청 전달).
- **직접 처리 및 제약:** 같은 파일의 변경이 섞여 범위 전달이 어렵거나, 모델 설정이 유효하지 않거나, 위임을 시작할 수 없으면 구현 에이전트가 직접 처리. 위임 중에는 같은 Git 인덱스에 쓰기 금지.
- **결과 확인 및 종료:** 커밋 해시·메시지·남은 변경을 전달받고 Git에서 확인한 뒤 사용자에게 보고하고 터미널 정리. 범위 질문이나 권한·검증 실패로 중단되면 터미널을 유지하고 사유 전달.

## 3. 공통 Herdr 위임 절차

1. **모델 설정:** 작업 트리의 [모델 매핑 기준](../../rules/models.mdc)에서 해당 키(`review` / `commit`)의 `model`과 `reasoning_effort`를 읽어 `delegate_model`, `delegate_effort`에 설정.
2. **세션 실행:** 부모의 `HC_TERMINAL_ID`와 Herdr 공간·탭 라벨을 확인하고 첫 프롬프트에 부모 주소를 전달한 뒤, 완료 시 최종 결과(리뷰 양식 또는 커밋 해시·메시지)를 `hc send <부모 주소>` 본문에 직접 담아 보고하며 중단 시에만 사유를 전달하도록 지시. 고유한 터미널 이름과 작업 트리 루트를 지정해 Codex를 백그라운드로 실행. 부모 주소나 공간·탭 라벨이 없거나 유효하지 않으면 임의로 선택하지 말고 위임 불가 사유를 보고:

```sh
parent_info=$(hc get "$HC_TERMINAL_ID" --json) || exit 1
herdr_space=$(printf '%s' "$parent_info" | python3 -c 'import json,sys; print(json.load(sys.stdin)["labels"]["herdr.space"])') || exit 1
herdr_tab=$(printf '%s' "$parent_info" | python3 -c 'import json,sys; print(json.load(sys.stdin)["labels"]["herdr.tab"])') || exit 1
[ -n "$herdr_space" ] && [ -n "$herdr_tab" ] || exit 1

hc run --bg --parent "$HC_TERMINAL_ID" \
  --label "herdr.space=$herdr_space" --label "herdr.tab=$herdr_tab" \
  --name "$delegate_agent" --cwd "$worktree_root" -- \
  sh -c '
    /usr/bin/env "PATH=$6" codex --no-daemon --model "$1" \
      --config "model_reasoning_effort=\"$2\"" "$3" ||
    hc send "$4" "[ABORT] $5 비정상 종료 (exit: $?)"
  ' _ "$delegate_model" "$delegate_effort" "$delegate_task" \
    "$HC_TERMINAL_ID" "$delegate_agent" "$PATH"

```
3. **이벤트 대기 및 상태 확인:** `hc run` 실행 직후에는 `hc wait`나 반복 폴링을 수행하지 않고 즉시 현재 응답 턴을 종료해 `hc send` 보고를 대기. 완료 또는 `[ABORT]` 보고가 입력되면 해당 단계의 처리 기준을 적용. 보고 없이 사용자 입력 등으로 턴이 재개되어 상태가 불명확한 경우에만 `hc get "$delegate_agent"`나 필요한 범위의 `hc read "$delegate_agent"`로 단발 확인하며, 결과가 불명확한 동안 동일 작업 재실행 금지.
4. **터미널 정리:** 각 단계 기준에 따라 결과 처리를 마친 뒤 `hc kill "$delegate_agent"`와 `hc rm "$delegate_agent"`로 위임 터미널 정리. 사용자 개입 대기 시에는 터미널을 유지하고 필요한 조치 전달.

## 4. 작업 상태 및 출력 규약

### 4-1. Todo 목록 유지 및 갱신 규칙

* **최초 생성:** 사전 단계(지침 로드 및 기존 코드 파악) 직후 전체 작업 단위를 분할해 최초 목록 생성.
* **순서 고정:** 최초 항목의 이름과 순서 유지. 진행 순서 변경이나 새 요구사항 추가 시에도 기존 항목 순서 변경 금지.
* **요구사항 반영:** 요구사항 변경 시 관련 항목을 즉시 갱신하거나 필요한 항목 추가.
* **항목 변경 제한:** 병합·분할·삭제는 요구사항 변경으로 기존 구성이 맞지 않거나 중복되어 진행 상태를 표현할 수 없는 경우에만 수행하며 변경 사유 짧게 명시.
* **재진행 처리:** 완료된 항목도 추가 요청·재검증 필요 시 미완료로 되돌리고 `재진행 중` 표시 후 재완료 시 최신 근거로 갱신.
* **생명주기:** 후속 요청이 기존 작업의 연속이면 새 목록으로 교체하지 않고 전체 작업 종료 시까지 유지.

### 4-2. 상시 출력 포맷 (매 턴 최하단 고정)

개발 진행 중 모든 응답의 최하단에 전체 Todo 목록과 완료 근거 유지·출력. Phase 1 생략 또는 리뷰·커밋 생략 시 사유 표시. 모든 개별 항목 완료 후에도 `작업 완료` 자동 체크 금지(`완료 확인 대기` 유지).

```text
📌 작업 목록
* [x] 작업 항목 1 — `근거: 수정된 파일/함수명, 컴파일/테스트 통과 여부 등`
* [x] 작업 항목 2 — `근거: 반영된 코드 스니펫 또는 검증 결과`
* [ ] 작업 항목 3 *(진행 중)* 또는 *(승인 대기)*
* [ ] 코드 리뷰 — `Phase 3. 코드 리뷰 실행` (또는 생략 사유)
* [ ] 커밋 — `Phase 4. 커밋 실행` (또는 생략 사유)
* [ ] 작업 완료 *(완료 확인 대기)*

```

### 4-3. 보고 및 종료 프로토콜

사용자 요청 유형에 따른 상태 전이 및 출력 양식 적용:

| 사용자 요청 | 상태 처리 및 개발 모드 여부 |
| --- | --- |
| **완료 보고 요청** | 현재 결과와 미완료 항목만 보고. **`작업 완료` 체크 및 모드 종료 금지** |
| **작업 완료 선언 / 승인** | 최종 결과 보고 후 **`작업 완료` 체크 및 개발 모드 종료** |
| **작업 종료(중단) 선언** | 미완료 항목과 중단 사유 기록 후 **`작업 완료`(종료 의미) 체크 및 개발 모드 종료** |

**보고/종료 시 출력 템플릿:**

```text
✅ 작업 요약
   * 구현 목적, 핵심 변경 사항과 검증 결과
   * 주요 설계·로직 결정 사항
📌 작업 목록
   * [x] 완료 항목 — 근거
   * [ ] 미완료 항목 — 현재 상태와 사유

```
