# 러스트 코드 리뷰

변경 코드가 요구사항과 계약을 충족하는지 검토하고, 품질 점수·변경 리스크·발견 사항을 근거와 함께 정리한다.

리뷰는 읽기 전용으로 수행. 코드·테스트·설정 등 사용자 파일을 직접 수정하지 않고 수정 방향만 제시한다. 검사에 필요한 빌드 산출물과 캐시는 허용하되, 테스트가 기존 데이터나 외부 상태를 변경할 수 있으면 격리된 환경에서 실행하고 불가능하면 미실행 사유를 보고한다.

## 진행 절차

1. **컨텍스트 확인:** 비교 기준(Base)과 대상 커밋, 변경 목적·계약, 영향받는 호출자 및 데이터 흐름 파악. 비교 기준과 대상 커밋, Rust·Cargo 버전, 실행 플랫폼과 검사에 사용한 feature를 기록. 변경과 관련된 지원 feature·플랫폼은 추가 검사하고 실행하지 못한 조합은 사유와 함께 미확인 범위에 기록.
2. **정적 검사(Deterministic):** 아래 명령을 순서대로 실행. `fmt` 또는 `clippy` 실패 시 결과와 수정 방향을 보고하고 리뷰 중단. 실행하지 않은 검사와 품질 점수·리스크는 `미평가`로 표시.
   - `cargo +nightly fmt --all -- --check` (종료 코드 0)
   - `cargo clippy --workspace --all-targets --locked -- -D warnings` (종료 코드 0, 경고 없음)
   - `cargo audit` (종료 코드·advisory를 알림으로 기록, 리뷰 차단 안 함)
3. **테스트 실행:** `cargo test --workspace --locked` 실행. 실패한 테스트의 이름·원인·영향과 수정 방향을 기록. ignored 테스트와 외부 서비스가 필요한 테스트의 실행 여부를 확인하고, 관련 테스트를 실행하지 못했다면 사유와 미확인 범위를 기록. 변경과 관련된 추가 feature·플랫폼 조합도 테스트하고 실행하지 못한 조합은 사유를 기록.
4. **리스크 분류:** 복구 가능성(단방향/양방향) 및 아키텍처 구조 변경 여부 평가.
5. **코드·테스트 평가:** 관련 기존 코드와 테스트를 읽고 필요한 실행 결과를 확인하여 6개 품질 항목 평가.
6. **결과 정리:** 지정된 출력 양식에 따라 판정, 리스크, 품질 점수, 발견 사항 도출.

## 품질 점수 (100점 환산)

각 항목을 `0~4점`으로 평가 후 정규화한다. 동일 근본 원인이 여러 항목에 영향을 주면 각 항목 점수에는 반영하되, 발견 사항은 중복 작성하지 않는다.

- **계산식:** `총점 = 100 × Σ(항목 점수 ÷ 4 × 배점) ÷ Σ(적용 항목 배점)`
- **예외 처리:**
  - `N/A`: 해당 변경과 무관한 항목은 사유를 적고 배점 합계에서 제외(억지 적용 금지).
  - `미확인`: 판단 근거가 부족하면 `N/A`나 `0점`으로 대체하지 않고 `미확인`으로 표기(총점·통과 판정 보류).

| 항목 | 배점 | 주요 확인 내용 |
| --- | ---: | --- |
| 기능 | 25 | 요구사항·계약 충족, 정상·실패·경계 조건, 기존 동작 호환성 |
| 가독성과 구조 | 15 | 식별자·흐름 명확성, 책임과 의존 방향, 기존 구조 활용, 불필요한 추상화·중복 배제 |
| 안정성 | 20 | 오류 처리, 상태 일관성, 동시성, 재시도·멱등성, 자원 정리 |
| 보안 | 20 | 인증·권한 경계, 입력 검증(`Parse, don't validate`), 민감정보 노출, 외부 의존성 |
| 성능 | 10 | 실제 부하 기준 시간·메모리·I/O 비용, 쿼리·반복 호출·자원 사용 회귀 |
| 테스트 용이성 | 10 | 계약 검증 인터페이스, 외부 의존성·시간 격리, 실패 재현, 기존 테스트 활용 |

- **점수 척도:** `4`(근거 확인 및 문제 없음) / `3`(주요 조건 충족, 사소한 개선) / `2`(동작·유지보수 보완 필요) / `1`(주요 조건 큰 결함) / `0`(핵심 계약 불성립)

## 변경 리스크

### 1. 복구 가능성
코드 복원뿐 아니라 배포 후 변경된 DB 상태와 외부 시스템 효과까지 포함해 판단한다.
- **양방향 (PR 롤백 가능):** 이전 코드 재배포만으로 데이터 보정이나 외부 조치 없이 기존 동작 복귀 가능.
- **단방향 (PR 롤백 불가):** 스키마·데이터 변환, 삭제, 외부 발송·결제 등 되돌릴 수 없는 효과가 있어 별도 복원·보정 절차 필요.
- **미확인:** 호환성 또는 영향받는 상태를 확인하지 못함.

### 2. 아키텍처 수준 구조 변경
단순 파일 이동·이름 변경이 아닌 **책임·모듈 경계, 의존 방향, 데이터 소유권, 공개 인터페이스 계약, 배포 단위 또는 동기·비동기 처리 방식**의 실질적 변화 여부를 확인한다.

### 3. 리스크 등급 판정
- **높음:** 단방향 변경(PR 롤백 불가)에 해당.
- **중간:** 양방향 변경(PR 롤백 가능)이나, 아키텍처 수준 구조 변경이 포함됨 (호출자·계약 호환성 추가 검증 필수).
- **낮음:** 양방향 변경이며 아키텍처 수준 구조 변경 없음.
- **미확인:** 복구 가능성 또는 아키텍처 영향 근거 부족 (판정 보류).

## 발견 사항 및 최종 판정

### 발견 사항 작성 규칙
- 모든 항목에 **위치, 발생 조건, 실제/예상 영향, 코드·실행 근거, 수정 방향**을 명시한다.
- 재현하지 못한 문제는 추론 근거와 확인 방법을 적으며, 단순 취향·가정 기반 개선 제안은 결함과 분리한다.
- **심각도:**
  - `치명`: 데이터 손실, 권한 우회, 광범위한 장애 (총점 무관 수정 필요)
  - `주요`: 요구사항·계약 위반, 핵심 실패 경로 결함 (총점 무관 수정 필요)
  - `경미`: 영향이 제한적인 가독성·구조 개선 (영향과 우선순위 기록)

### 최종 판정 순서
1. **수정 필요:** `치명`·`주요` 발견 사항이 있거나, 적용 항목 중 `2점 이하`가 존재하거나, 총점이 `80점 미만`이거나, `fmt`/`clippy` 실패 또는 코드 결함에 의한 테스트 실패 시. 원인과 수정 방향 제시.
2. **판정 보류:** 수정 필요 사유는 없으나, 테스트 실패가 환경 문제인지 코드 결함인지 확인되지 않거나, `미확인` 항목이 있거나 리스크 등급 판정의 필수 근거가 부족할 때.
3. **통과:** 모든 적용 항목이 `3점 이상`, `총점 80점 이상`, 리스크 확인 완료 시. (검토한 커밋 범위에 대한 판단이며 전체 배포 승인을 의미하지 않음)
