# 코드 리뷰

변경 코드가 요구사항과 계약을 충족하고 코드베이스의 책임 배치, 계층 역할, 의존 경계를 일관되게 따르는지 검토한다. 품질 점수·변경 리스크·발견 사항을 근거와 함께 정리한다.

리뷰는 읽기 전용으로 수행한다. 코드·테스트·설정 등 사용자 파일은 직접 수정하지 않고 수정 방향만 제시한다. 검사에 필요한 빌드 산출물과 캐시는 허용한다.

---

## 진행 절차

1. 스택 지침 로드 및 컨텍스트 확인:
   - 변경 대상에 해당하는 스택 지침을 먼저 로드한다(풀스택 변경이면 둘 다 로드).
     - Rust 백엔드·시스템: [Rust 리뷰 지침](references/rust.md)
     - 프런트엔드 UI: [프런트엔드 리뷰 지침](references/frontend.md)
   - 비교 기준(Base)과 대상 커밋, 변경 목적·계약, 영향받는 호출자·사용자 흐름·데이터 흐름을 파악하고 스택 지침에 명시된 검사 환경 정보를 기록한다.
2. 정적 검사(Deterministic):
   - 스택 지침에 지정된 정적 검사 명령을 순서대로 실행한다.
   - 필수 정적 검사 실패 시 결과와 수정 방향을 보고하고 리뷰를 중단한다. 실행하지 않은 검사와 품질 점수·리스크는 `미평가`로 표시한다.
   - 실행할 수 없는 명령은 사유와 미확인 범위를 기록하고 판정을 보류한다.
3. 테스트 및 동작·화면 확인:
   - 스택 지침에 따라 자동 테스트(및 프런트엔드의 경우 화면·키보드·뷰포트 상태)를 실행·확인한다.
   - 실패한 테스트의 이름·원인·영향과 수정 방향을 기록한다. 실행하지 못한 테스트, 환경 조합, 화면 상태는 사유와 함께 미확인 범위에 기록한다.
4. 리스크 분류: 복구 가능성(단방향/양방향) 및 아키텍처 수준 구조 변경 여부를 평가한다.
5. 코드·테스트 평가: 관련 기존 코드와 테스트를 읽고 실행 결과를 확인해 스택 지침의 7개 품질 항목을 평가한다. 아키텍처 일관성은 아래의 질문 제기 → 근거 확인 → 평가를 필요한 만큼 반복하여 검토한다. 확인하지 못한 내용은 추정으로 채우지 않는다.
6. 결과 정리: 지정된 출력 양식에 따라 판정, 리스크, 품질 점수, 발견 사항을 정리한다.

---

## 품질 점수 (100점 환산)

각 항목을 `0~4점`으로 평가 후 정규화한다. 동일 근본 원인이 여러 항목에 영향을 주면 각 점수에는 반영하되, 발견 사항은 중복 작성하지 않는다.

- 계산식: `총점 = 100 × Σ(항목 점수 ÷ 4 × 배점) ÷ Σ(적용 항목 배점)`
- 예외 처리:
  - `N/A`: 해당 변경과 무관한 항목은 사유를 적고 배점 합계에서 제외한다(억지 적용 금지).
  - `미확인`: 판단 근거가 부족하면 `N/A`나 `0점`으로 대체하지 않고 `미확인`으로 표기한다. 총점과 통과 판정은 보류한다.
- 점수 척도: `4`(근거 확인 및 문제 없음) / `3`(주요 조건 충족, 사소한 개선) / `2`(동작·유지보수 보완 필요) / `1`(주요 조건 큰 결함) / `0`(핵심 계약 불성립)
- 항목 구성 및 배점: 스택 지침의 배점표를 따른다(풀스택 변경 시 스택별 항목표를 각각 산출해 병기).

### 아키텍처 일관성

1. 질문 제기 — 이번 변경에서 내린 설계 선택을 짚고, 시니어 리뷰어 관점에서 답에 따라 평가가 달라질 구체적인 질문을 세운다. 질문의 수와 깊이는 변경 영향에 맞춘다(세부 관점은 스택 지침 참고).
   - 관점 — 정책 판단의 소유 주체는 누구인가? 정책이 바뀌면 어느 주체가 판단을 수정해야 하며, 새 호출자·화면이 같은 결정을 중복 수행하는가?
   - 계층 — 이 처리가 현재 계층의 역할에 맞는가? 기존 책임을 우회하거나 여러 계층에 분산하는가?
   - 경계 — 새 의존이나 데이터 접근으로 어느 모듈이 다른 모듈의 내부 변경에 영향을 받는가? 공개 계약과 데이터 소유권을 따르는가?
2. 근거 확인 — 변경 경로와 같은 책임을 수행하는 기존 경로를 비교하고, 호출 흐름·공개 계약·의존 관계·테스트에서 답과 근거 위치를 찾는다. 기존 구현이 서로 다르면 책임을 소유하는 구현과 그 계약을 근거로 삼는다. 비교 대상이 없는 신규 경로는 연결되는 모듈의 계약과 의존 관계를 확인한다. 결론에 필요한 설계 의도가 자료에서 확인되지 않으면 작성자에게 확인할 질문을 남긴다.
3. 평가 — 확인한 답을 변경 목적과 기존 책임 배치에 비추어 평가하고 호출자·화면·유지보수에 생기는 영향을 설명한다. 의도적인 구조 변경은 변경 목적, 새 책임 소유자, 영향받는 경로의 전환 범위와 계약 호환성을 근거로 평가한다. 이번 변경이 새로 만들거나 적용 범위를 넓힌 위반을 발견 사항에 포함한다. 평가에 필요한 근거가 부족하면 `미확인`으로 기록한다.

후속 질문과 종료

- 답을 확인할 때마다 새로 드러난 책임·의존 관계나 반대 근거를 살핀다. 후속 질문의 답에 따라 일관성 평가, 영향받는 경로, 발견 사항의 심각도 또는 수정 방향이 달라질 수 있으면 질문 제기로 돌아간다. 위반을 하나 확인한 뒤에도 그 위반의 범위나 심각도를 바꿀 수 있는 경로는 확인한다.
- 검토 완료 — 판단에 필요한 답을 근거로 확인했고, 변경의 영향 범위에서 결론을 바꿀 열린 질문이 없으면 해당 쟁점의 검토를 끝낸다. 결론을 뒷받침하는 근거와 확인한 범위를 남긴다.
- 미확인 — 결론을 바꿀 질문에 답할 근거를 현재 검토에서 확보할 수 없으면 해당 쟁점은 `미확인`으로 남긴다. 남은 질문, 부족한 근거, 답을 얻는 데 필요한 확인을 기록하고 다른 쟁점의 검토를 이어간다.

평가 결론에 영향을 준 최초·후속 질문의 연결, 답과 근거 위치, 평가와 영향, 종료 근거를 출력의 아키텍처 일관성 검토에 남긴다. 구조가 타당하다는 결론에 도달한 주요 질문도 포함한다. 관련 쟁점이 없거나 검토하지 못한 경우에는 해당 사유를 한 줄로 기록한다.

### 코드 밀도 및 과잉 설계 점검

스택 지침에 정의된 과잉 설계·군더더기 항목이 발견되면 영향 범위에 따라 `경미`(가독성·유지보수 저하) 또는 `주요`(동시성 블로킹·상태 불일치·계약 왜곡) 발견 사항으로 기록하고 단순화 방향을 제시한다.

## 변경 리스크

### 1. 복구 가능성

코드 복원뿐 아니라 배포 후 변경된 DB·서버 데이터, 브라우저 저장 데이터와 외부 시스템 효과까지 포함해 판단한다.

- 양방향 (PR 롤백 가능): 이전 코드 재배포만으로 데이터 보정이나 외부 조치 없이 기존 동작으로 복귀 가능.
- 단방향 (PR 롤백 불가): 스키마·데이터 변환, 삭제, 외부 발송·결제 등 되돌릴 수 없는 효과가 있어 별도 복원·보정 절차 필요.
- 미확인: 배포 호환성 또는 영향받는 상태를 확인하지 못함.

### 2. 아키텍처 수준 구조 변경

단순 파일 이동·이름 변경이 아닌 책임·모듈 경계, 의존 방향, 상태·데이터 소유권, 라우팅·공개 인터페이스 계약, 배포 단위 또는 동기·비동기 처리 방식의 실질적 변화 여부를 확인한다.

구조 변경 여부와 복구 가능성은 리스크 등급에 반영한다. 경계 위반의 심각도는 영향받는 경로와 책임을 근거로 판정한다.

### 3. 리스크 등급 판정

- 높음: 단방향 변경(PR 롤백 불가)에 해당.
- 중간: 양방향 변경(PR 롤백 가능)이나 아키텍처 수준 구조 변경이 포함됨(호출자·계약 호환성 추가 검증 필수).
- 낮음: 양방향 변경이며 아키텍처 수준 구조 변경 없음.
- 미확인: 복구 가능성 또는 아키텍처 영향의 근거 부족(판정 보류).

## 발견 사항 및 최종 판정

### 발견 사항 작성 규칙

- 모든 항목에 위치, 발생 조건, 실제/예상 영향, 코드·실행 근거, 수정 방향을 명시한다.
- 아키텍처 일관성 발견 사항에는 기존 책임 또는 경계의 근거 위치, 변경이 위반한 지점, 영향받는 호출자·화면 경로와 책임을 둘 위치를 기록한다.
- 재현하지 못한 문제는 추론 근거와 확인 방법을 적으며, 단순 취향·가정 기반 개선 제안은 결함과 분리한다.
- 심각도:
  - `치명`: 데이터 손실, 권한 우회, 광범위한 장애(총점 무관 수정 필요).
  - `주요`: 요구사항·계약 위반, 핵심 실패·사용자 흐름 또는 접근성 결함, 근거가 확인된 책임 중복·계층 우회·경계 위반의 신규 발생 또는 확산(총점 무관 수정 필요).
  - `경미`: 영향이 제한적인 UI·가독성·구조 개선, 과잉 설계 단순화(영향과 우선순위 기록).

### 최종 판정 순서

1. 수정 필요: `치명`·`주요` 발견 사항이 있거나, 적용 항목 중 `2점 이하`가 존재하거나, 총점이 `80점 미만`이거나, 필수 정적 검사 실패 또는 코드 결함에 의한 테스트 실패 시. 원인과 수정 방향 제시.
2. 판정 보류: 수정 필요 사유는 없으나 실패 원인이 환경 문제인지 코드 결함인지 확인되지 않거나, `미확인` 항목이 있거나 리스크 등급 판정의 필수 근거가 부족할 때.
3. 통과: 모든 적용 항목이 `3점 이상`, `총점 80점 이상`, 리스크 확인 완료 시. 아키텍처 일관성은 적용 여부와 판단 근거를 명시한다(검토한 변경 범위에 대한 판단이며 전체 배포 승인을 의미하지 않음).
