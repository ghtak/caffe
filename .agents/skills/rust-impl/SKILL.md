# Rust 코드 구현 워크플로우

## 적용 기준

- 신규 기능 추가, 도메인 모델링, 공개 계약 변경이 포함된 작업은 기본값으로 Phase 1부터 적용
- 범위가 명확한 단순 버그 수정이나 내부 리팩토링은 Phase 1 없이 바로 구현 가능
- 사용자의 명시적 지시가 이 워크플로우보다 우선

## 진행 상태 및 산출물 관리 규칙

### 작업 목록 유지

- 최초 작업 목록을 기준으로 기존 항목의 이름과 순서를 유지한다.
- 새 요구사항은 관련 기존 항목을 갱신하거나 필요한 새 항목을 추가한다.
  진행 순서가 달라져도 목록 순서는 변경하지 않는다.
- 항목 병합·분할·삭제는 요구사항 변경으로 기존 구성이 더 이상 맞지 않거나
  중복되어 진행 상태를 정확히 표현할 수 없는 경우에만 수행한다.
  변경 시 이유를 짧게 명시한다.
- 완료된 항목도 추가 요청이나 재검증이 필요하면 다시 진행할 수 있다.
  해당 항목을 미완료로 전환하고 `재진행 중`으로 표시하며,
  재완료 시 최신 완료 근거로 갱신한다.
- 작업 목록은 전체 작업이 종료될 때까지 유지한다.
  후속 요청이 기존 작업의 연속이면 새 목록으로 교체하지 않는다.

### 전체 작업 완료와 종료

- 개별 항목의 완료 여부는 실제 수행·검증 결과에 따라 표시한다.
- 모든 개별 항목을 완료해도 `작업 완료`는 자동으로 체크하지 않는다.
  사용자에게 결과를 보고하고 `완료 확인 대기`로 유지한다.
- 사용자가 작업 완료를 선언하거나 완료를 승인한 경우에만
  `작업 완료`를 체크하고 개발 모드를 종료한다.
- 사용자가 종료를 선언하면 미완료 항목은 그대로 두고 중단 사유를 기록한다.
  `작업 완료`는 종료 의미로 체크한다.
- 완료 보고 요청만으로는 완료 승인이나 종료를 추정하지 않는다.

### 1. 개발 진행 중 (매 턴 최하단 고정 출력)

작업 시작 시(Phase 1 코드 파악 직후 또는 즉시 구현 진입 시) 전체 작업 단위를 쪼개어 최초 목록을 생성.
개발 작업이 진행되는 동안 모든 응답의 마지막에 전체 Todo 목록과 완료 근거를 유지하여 출력. 
대화 중 요구사항이 추가·수정·삭제되면 즉시 목록에 반영하여 최신 상태를 유지.

--- 
```
📌 작업 목록 
* [x] 작업 항목 1 — `근거: 수정된 파일/함수명, 컴파일/테스트 통과 여부 등`
* [x] 작업 항목 2 — `근거: 반영된 코드 스니펫 또는 검증 결과`
* [ ] 작업 항목 3 *(진행 중)* 또는 *(승인 대기)*
* [ ] 작업 항목 4
* [ ] 코드 리뷰 - `Phase 3. 코드 리뷰 실행`
* [ ] 커밋 - `Phase 4. 커밋 실행`
* [ ] 작업 완료
```

### 2. 작업 완료 보고 또는 종료 시

- 사용자가 완료 보고를 요청하면 현재 결과와 미완료 항목을 보고한다.
  보고 요청만으로 `작업 완료`를 체크하거나 개발 모드를 종료하지 않는다.
- 사용자가 작업 완료를 선언하거나 승인하면 최종 결과를 보고하고
  `작업 완료`를 체크한 뒤 개발 모드를 종료한다.
- 사용자가 작업 종료를 선언하면 미완료 항목과 중단 사유를 기록하고,
  `작업 완료`를 종료 의미로 체크한 뒤 개발 모드를 종료한다.
  
```
✅ 작업 요약
   * 구현 목적과 핵심 변경 사항
   * 주요 설계·로직 결정 사항이 있으면 기재
📌 작업 목록 
   * [x] 완료 항목 — 근거
   * [ ] 미완료 항목 — 현재 상태와 사유
```

## Phase 1. 계약 및 골격

- 구현 전 관련 기존 코드와 테스트를 확인해 구조·계약·관례를 파악. 기존 구현은 참고하되 요청과 책임·경계에 맞게 적용. 더 적합한 방식이 있으면 근거를 추가하여 적용.
- 목적, 책임, 경계를 기준으로 엔터티, 오류, 입출력 타입, 인터페이스와 함수 시그니처 작성(가독성 우선)
- 단순 생성자·접근자를 제외한 신규 함수 본문은 `todo!("주요 계약 조건과 제약 사항")`와 같이 작성. 1~2문장. 읽기 편하게
- 비즈니스 로직, DB 쿼리, 외부 API 호출은 구현하지 않음
- `cargo check`와 모듈 가시성(`pub`) 확인. 테스트는 작성하지 않음
- 골격 작성 후 사용자 리뷰 요청. 승인 전 상세 구현에 진입하지 않음

## Phase 2. 상세 구현 및 검증

- 사용자가 승인한 기능 범위의 `todo!()`를 실제 로직으로 교체
- 테스트는 변경의 위험과 검증 가치에 따라 선택. 핵심 계약과 실제로 발생 가능한 경계·실패 상황 중심으로 작성
- 테스트를 추가·수정할 때는 [test-guide](../test-guide/SKILL.md)를 읽고 적용
- 변경에 적합한 포맷·검증 명령 실행. 구현 후 cargo +nightly fmt --all --로 포맷하고, 필요에 따라 cargo test, clippy 등 실행.
- Phase 1 생략 시 요청 범위에서 바로 구현. 이미 승인된 계약은 재승인 없이 진행. 승인 범위를 벗어나는 계약 변경은 영향과 대안 제시 후 확인
- 구현후 추가·수정한 테스트를 test-guide와 기존 모듈 관례에 맞게 정리. 테스트 코드는 모듈의 하단으로 이동
- 구현후 책임·경계 자체 점검 수행

### 책임·경계 자체 점검

- 구현자가 변경한 코드의 책임과 경계를 다음 항목으로 점검:

1. 각 구성 요소가 맡은 책임과 상태 소유권을 지키는가?
2. 신뢰 경계에서 보장이 필요한 값을 적절히 검증·변환하는가?
3. 도메인이 구체적인 전달 방식(HTTP 등)이나 인프라(DB 등)에 불필요하게 의존하는가?
4. 변경한 계약과 협력 관계가 호출자에게 명확한가?

- 위반 발견 시 위치·원인·대안을 보고하고 사용자 판단 요청. 위반이 없으면 리뷰 완료 보고.

## Phase 3. 코드 리뷰

- 사용자가 리뷰를 요청하면 Herdr 서브에이전트에 변경 범위와 `rust-review` 스킬 적용을 명시해 리뷰를 위임.
- 구현자가 직접 수행한 검토는 이 단계를 대체하지 않는다.
- 서브에이전트로부터 발견 사항의 위치·심각도·근거와 검증 결과를 전달받아 확인 후 사용자에게 보고.
- 서브에이전트를 사용할 수 없거나 리뷰 결과를 확인할 수 없으면 사유를 보고하고 리뷰를 완료로 표시하지 않는다.
- 사용자가 리뷰를 건너뛰도록 요청한 경우 생략.


## Phase 4. 커밋

- 사용자가 커밋을 요청하면 [commit](../commit/SKILL.md) 스킬을 사용
- 사용자가 커밋을 건너뛰도록 요청한 경우 생략.
