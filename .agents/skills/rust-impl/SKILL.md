# Rust 코드 구현 워크플로우

## 1. 진입 기준

- **Phase 1 시작 (기본값):** 신규 기능 추가, 도메인 모델링, 공개 계약 변경 포함 시 적용.
- **Phase 2 즉시 시작:** 범위가 명확한 단순 버그 수정 또는 내부 리팩토링 시 적용.
- **우선순위:** 사용자의 명시적 지시가 기본 진입 기준보다 우선함.

---

## 2. 작업 파이프라인

### Phase 1. 계약 및 골격 설계 (승인 게이트)

1. **기존 코드 파악:** 관련 코드와 테스트를 확인해 구조·계약·관례 파악. 기존 패턴을 참고하되 요청의 책임·경계에 더 적합한 방식이 있으면 근거와 함께 적용.
2. **골격 작성:** 목적·책임·경계를 기준으로 엔터티, 오류, 입출력 타입, 인터페이스 및 함수 시그니처 작성(가독성 우선).
3. **본문 스텁 처리:** 단순 생성자·접근자를 제외한 신규 함수 본문은 `todo!("주요 계약 조건과 제약 사항")` 형태로 1~2문장 이내 작성. 비즈니스 로직, DB 쿼리, 외부 API 호출 구현 금지.
4. **컴파일 및 가시성 확인:** `cargo check` 및 모듈 가시성(`pub`)만 확인. 테스트 작성 금지.
5. **승인 요청:** 골격 작성 후 사용자 리뷰 요청. **승인 전 상세 구현(Phase 2) 진입 금지.**

---

### Phase 2. 상세 구현 및 자체 검증

#### 2-1. 로직 구현 및 테스트
- 승인된 범위의 `todo!()`를 실제 로직으로 교체(Phase 1 생략 시 요청 범위 즉시 구현).
- 이미 승인된 계약은 재승인 없이 진행하되, 승인 범위를 벗어나는 계약 변경이 필요하면 영향과 대안을 먼저 제시하고 확인받음.
- 테스트 추가 여부는 변경의 위험과 검증 가치에 따라 판단하며, 필요한 경우 핵심 계약과 실제 발생 가능한 경계·실패 상황을 검증.
- 테스트 추가·수정 시 [test-guide](../test-guide/SKILL.md)와 [Rust 테스트 지침](../test-guide/references/rust.md) 적용.

#### 2-2. 포맷 및 정적 검증
- 구현 후 `cargo +nightly fmt --all --`로 포맷팅.
- 변경 규모와 위험도에 맞춰 `cargo test`, `cargo clippy` 등 검증 명령 실행 및 통과 확인.

#### 2-3. 책임·경계 자체 점검
구현 완료 후 변경 코드 대상 아래 4가지 항목 자체 점검. 위반 발견 시 위치·원인·대안 보고 및 사용자 판단 요청, 이상 없을 시 자체 점검 완료 보고.
1. 각 구성 요소가 맡은 책임과 상태 소유권을 지키는가?
2. 신뢰 경계에서 보장이 필요한 값을 적절히 검증·변환하는가?
3. 도메인이 구체적인 전달 방식(HTTP 등)이나 인프라(DB 등)에 불필요하게 의존하는가?
4. 변경한 계약과 협력 관계가 호출자에게 명확한가?

---

### Phase 3. 코드 리뷰 (위임 게이트)

- **실행 조건:** 사용자가 리뷰를 요청한 경우에만 [rust-review](../rust-review/SKILL.md) 스킬 적용(건너뛰기 요청 시 생략). 구현자 자체 점검은 Phase 2 완료 근거로만 사용.
- **위임 규칙:** 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차) 사용(모델 키: `review`). 첫 메시지에 `$rust-review` 적용, 변경 목적·계약, 비교 기준, 검토 대상을 전달하며 리뷰 중 검토 대상 수정 금지.
- **예외 처리:** 모델 설정이 유효하지 않거나 위임 또는 결과 확인이 불가능하면 사유를 보고하고 리뷰를 미완료 상태로 유지.
- **결과 확인 및 종료:**
  - 서브에이전트로부터 [rust-review 출력 양식](../rust-review/SKILL.md#출력-양식)에 따른 보고를 받아 검토 범위와 근거를 확인한 뒤 사용자에게 전달.
  - 결함이나 `fmt`·`clippy` 실패를 근거와 함께 보고했다면 리뷰 결과로 처리. `수정 필요` 판정도 결과 확인 후 터미널 정리.
  - 범위 확인이나 권한 승인 등 사용자 개입 후 이어갈 작업이 있으면 터미널 유지.

---

### Phase 4. 커밋 (위임 게이트)

- **실행 조건:** 사용자가 커밋을 요청한 경우에만 [commit](../commit/SKILL.md) 스킬 적용.
- **범위 정리 및 위임:** 작업 목적, 포함·제외할 변경, 기존 staged 변경 처리 범위를 정리. 범위를 명확히 전달할 수 있으면 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차)로 위임(모델 키: `commit`, 첫 메시지에 `$commit` 적용과 실제 커밋 요청 전달).
- **직접 처리 및 제약:** 같은 파일의 변경이 섞여 범위 전달이 어렵거나, 모델 설정이 유효하지 않거나, 위임을 시작할 수 없으면 구현 에이전트가 직접 처리. 위임 중에는 같은 Git 인덱스에 쓰기 금지.
- **결과 확인 및 종료:** 커밋 해시·메시지·남은 변경을 전달받고 Git에서 확인한 뒤 사용자에게 보고하고 터미널 정리. 범위 질문이나 권한·검증 실패로 중단되면 터미널을 유지하고 사유 전달.

---

## 3. 공통 Herdr 위임 절차

1. **모델 설정:** 작업 트리의 [모델 매핑 기준](../../rules/models.mdc)에서 해당 키(`review` / `commit`)의 `model`과 `reasoning_effort`를 읽어 `delegate_model`, `delegate_effort`에 설정.
2. **백그라운드 실행:** 부모의 `HC_TERMINAL_ID`를 첫 프롬프트에 전달하고, 완료·중단 시 `hc send <부모 주소> "<결과 또는 중단 사유>"`로 보고하도록 지시. 고유한 터미널 이름과 작업 트리 루트를 지정해 실행:
   ```sh
   hc run --bg --name "$delegate_agent" --cwd "$worktree_root" -- \
     codex --no-daemon --model "$delegate_model" \
       --config "model_reasoning_effort=\"$delegate_effort\"" "$delegate_task"
   hc wait --timeout 30 "$delegate_agent"
   ```
3. **상태 확인:** 시작 직후 대기 상태나 시간 초과만으로 완료 판단 금지. 보고가 없고 상태가 불명확하면 `hc get`이나 필요한 범위의 `hc read`로 확인. 시간 초과 후에도 작업 중이면 같은 터미널을 대상으로 `hc wait` 재실행. 완료·중단 보고를 받거나 사용자 개입이 필요해지면 해당 단계의 처리 기준 적용. 실행 여부나 결과가 불명확한 동안 동일 작업 재실행 금지.
4. **터미널 정리:** 각 단계 기준에 따라 결과 확인 후 `hc kill`과 `hc rm`으로 터미널 정리. 사용자 개입 대기 시 터미널을 유지하고 필요한 조치 전달.

## 4. 작업 상태 및 출력 규약

### 4-1. Todo 목록 유지 및 갱신 규칙

- **최초 생성:** Phase 1 코드 파악 직후(또는 Phase 2 즉시 진입 시) 전체 작업 단위를 분할해 최초 목록 생성.
- **순서 고정:** 최초 항목의 이름과 순서 유지. 진행 순서 변경이나 새 요구사항 추가 시에도 기존 항목 순서 변경 금지.
- **요구사항 반영:** 요구사항 변경 시 관련 항목을 즉시 갱신하거나 필요한 항목 추가.
- **항목 변경 제한:** 병합·분할·삭제는 요구사항 변경으로 기존 구성이 맞지 않거나 중복되어 진행 상태를 표현할 수 없는 경우에만 수행하며 변경 사유 짧게 명시.
- **재진행 처리:** 완료된 항목도 추가 요청·재검증 필요 시 미완료로 되돌리고 `재진행 중` 표시 후 재완료 시 최신 근거로 갱신.
- **생명주기:** 후속 요청이 기존 작업의 연속이면 새 목록으로 교체하지 않고 전체 작업 종료 시까지 유지.

### 4-2. 상시 출력 포맷 (매 턴 최하단 고정)

개발 진행 중 모든 응답의 최하단에 전체 Todo 목록과 완료 근거 유지·출력. 모든 개별 항목 완료 후에도 `작업 완료` 자동 체크 금지(`완료 확인 대기` 유지).

---

```text
📌 작업 목록
* [x] 작업 항목 1 — `근거: 수정된 파일/함수명, 컴파일/테스트 통과 여부 등`
* [x] 작업 항목 2 — `근거: 반영된 코드 스니펫 또는 검증 결과`
* [ ] 작업 항목 3 *(진행 중)* 또는 *(승인 대기)*
* [ ] 작업 항목 4
* [ ] 코드 리뷰 - `Phase 3. 코드 리뷰 실행`
* [ ] 커밋 - `Phase 4. 커밋 실행`
* [ ] 작업 완료 *(완료 확인 대기)*
```

### 4-3. 보고 및 종료 프로토콜

사용자 요청 유형에 따른 상태 전이 및 출력 양식 적용:

| 사용자 요청 | 상태 처리 및 개발 모드 여부 |
| :--- | :--- |
| **완료 보고 요청** | 현재 결과와 미완료 항목만 보고. **`작업 완료` 체크 및 모드 종료 금지** |
| **작업 완료 선언 / 승인** | 최종 결과 보고 후 **`작업 완료` 체크 및 개발 모드 종료** |
| **작업 종료(중단) 선언** | 미완료 항목과 중단 사유 기록 후 **`작업 완료`(종료 의미) 체크 및 개발 모드 종료** |

**보고/종료 시 출력 템플릿:**

```text
✅ 작업 요약
   * 구현 목적과 핵심 변경 사항
   * 주요 설계·로직 결정 사항
📌 작업 목록
   * [x] 완료 항목 — 근거
   * [ ] 미완료 항목 — 현재 상태와 사유
```
