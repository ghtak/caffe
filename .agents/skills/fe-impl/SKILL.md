# 프런트엔드 구현 워크플로우

## 적용 기준

- 신규 화면·기능, 사용자 흐름 또는 공개 UI 계약 변경은 기본값으로 Phase 1부터 적용
- 범위가 명확한 단순 버그 수정이나 내부 리팩토링은 Phase 1 없이 바로 구현 가능
- 사용자의 명시적 지시가 이 워크플로우보다 우선
- 작업 전 [프런트엔드 구조 가이드](../../../docs/agents/frontend_structure.md)를 확인하고 관련 구조·의존성·상태 관리·스타일링 기준 적용

## 진행 상태 및 산출물 관리

### 작업 목록 유지

- 작업 시작 시 전체 작업 단위를 나누고 최초 목록의 항목 이름과 순서를 유지한다.
- 요구사항이 바뀌면 관련 항목을 갱신하거나 필요한 항목을 추가한다.
- 항목 병합·분할·삭제가 필요하면 이유를 짧게 명시한다.
- 완료된 항목도 추가 요청이나 재검증이 필요하면 재진행하고 완료 근거를 갱신한다.
- 후속 요청이 기존 작업의 연속이면 목록을 교체하지 않는다.

### 전체 작업 완료와 종료

- 개별 항목은 실제 수행·검증 결과에 따라 완료 표시한다.
- 모든 항목을 완료해도 사용자에게 결과를 보고하고 `완료 확인 대기`로 유지한다.
- 사용자가 완료를 선언하거나 승인하면 `작업 완료`를 체크하고 개발 모드를 종료한다.
- 사용자가 종료를 선언하면 미완료 항목과 중단 사유를 기록하고 개발 모드를 종료한다.
- 완료 보고 요청만으로 완료 승인이나 종료를 추정하지 않는다.

### 개발 진행 중

개발 작업이 진행되는 동안 모든 응답의 마지막에 전체 작업 목록과 완료 근거를 출력한다.

```text
📌 작업 목록
* [ ] 화면·상태 계약 및 정적 시안
* [ ] 상세 구현 및 검증
* [ ] 책임·경계 자체 점검
* [ ] 코드 리뷰 — Phase 3
* [ ] 커밋 — Phase 4
* [ ] 작업 완료
```

각 항목에 진행 상태와 확인 가능한 완료 근거를 기재한다.
Phase 1을 생략하거나 리뷰·커밋을 건너뛰면 해당 사유를 표시한다.

### 완료 보고 또는 종료 시

구현 목적, 핵심 변경, 주요 결정과 검증 결과를 보고한다.
작업 목록에는 완료 근거와 미완료 사유를 유지한다.

## Phase 1. 화면·상태 계약 및 정적 시안

- 관련 코드, 테스트와 기존 UI 컴포넌트를 확인해 구조·관례·재사용 가능성을 파악한다.
- 화면 목적과 사용자 흐름을 기준으로 필요한 라우트, 레이아웃, 컴포넌트와 각 구성 요소의 책임·상태 소유권을 정한다.
- 필요한 범위에서 입력과 출력, URL 파라미터, API 계약, 로딩·빈 결과·오류 상태, 사용자 동작 및 접근성 요구를 정리한다.
- 프로젝트 구조와 의존성 경계를 존중해 타입·인터페이스와 컴포넌트 골격을 작성한다. 기존 계약이 불명확하면 확인된 사실과 가정을 구분한다.
- 화면 구성과 시각적 방향을 확인할 수 있도록 정적 시안을 작성한다. 필요한 경우 대표 상태와 예시 데이터를 표시한다.
- 정적 시안에서 실제 비즈니스 로직이나 API 연동은 구현하지 않는다. 예시 데이터와 미동작 요소는 시안 리뷰 시 명확히 알린다.
- 타입 검사와 import 경계를 확인한다. 이 단계에서는 테스트를 작성하지 않는다.
- 골격, 주요 계약과 정적 시안을 사용자에게 보고하고 리뷰를 요청한다. 승인 전 상세 구현에 진입하지 않는다.

## Phase 2. 상세 구현 및 검증

- 승인된 기능 범위와 계약에 따라 화면·상태 전이·데이터 연동을 구현한다.
- 서버 상태, 전역 UI 상태, URL 상태와 로컬 입력 상태의 소유권을 구분한다.
- 프런트엔드 구조 가이드의 데이터 요청·스타일링 규칙을 적용한다.
- 변경 위험과 검증 가치에 따라 테스트를 선택한다. 사용자에게 중요한 동작과 실제 발생 가능한 로딩·빈 결과·실패 상황을 중심으로 검증한다.
- 테스트를 추가·수정할 때는 [test-guide](../test-guide/SKILL.md)를 읽고 적용한다.
- 프로젝트에서 제공하는 타입 검사와 빌드 등 변경에 적합한 검증 명령을 실행한다.
- UI 변경은 가능한 환경에서 실제 화면을 확인한다. 확인하지 못한 화면이나 상태는 검증 결과에 명시한다.
- Phase 1 생략 시 요청 범위에서 바로 구현한다. 이미 승인된 계약은 재승인하지 않는다. 승인 범위를 벗어나는 계약 변경이 필요하면 영향과 대안을 제시하고 확인한다.
- 구현 후 책임·경계 자체 점검을 수행한다.

### 책임·경계 자체 점검

1. 각 화면과 컴포넌트가 맡은 책임과 상태 소유권을 지키는가?
2. 라우트·feature·shared 사이의 의존성이 프로젝트 경계를 지키는가?
3. 외부 데이터와 URL 입력을 필요한 경계에서 검증·변환하는가?
4. 로딩·빈 결과·오류 상태와 사용자 동작이 계약에 맞게 처리되는가?
5. 키보드 사용, 의미 있는 마크업 등 변경 범위에 필요한 접근성을 충족하는가?
6. 변경한 UI 계약과 구성 요소 간 관계가 호출자에게 명확한가?

위반 발견 시 위치·원인·대안을 보고하고 사용자 판단을 요청한다. 위반이 없으면 자체 점검 완료를 보고한다.

## Phase 3. 코드 리뷰

- 사용자가 리뷰를 요청하면 별도 서브에이전트에 변경 범위와 [fe-review](../fe-review/SKILL.md) 스킬 적용을 명시해 리뷰를 위임한다.
- 구현자가 직접 수행한 자체 점검은 이 단계를 대체하지 않는다.
- 발견 사항의 위치·심각도·근거와 검증 결과를 확인해 사용자에게 보고한다.
- 서브에이전트를 사용할 수 없거나 리뷰 결과를 확인할 수 없으면 사유를 보고하고 리뷰를 완료로 표시하지 않는다.
- 사용자가 리뷰를 건너뛰도록 요청하면 생략한다.

## Phase 4. 커밋

- 사용자가 커밋을 요청하면 [commit](../commit/SKILL.md) 스킬을 사용한다.
- 사용자가 커밋을 건너뛰도록 요청하면 생략한다.
