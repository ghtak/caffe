# 프런트엔드 구현 워크플로우

## 1. 진입 기준

- **Phase 1 시작 (기본값):** 상위 스펙이나 시각 시안 없이 신규 화면·기능, 사용자 흐름, 공개 UI 계약을 처음 설계·구현할 때 적용.
- **Phase 2 즉시 시작:**
  - `macro-spec` 등 상위 설계 문서에서 화면 흐름과 API 계약이 이미 확정된 개별 태스크 구현
  - 범위가 명확한 단순 버그 수정 또는 내부 리팩토링
- **우선순위:** 사용자의 명시적 지시가 기본 진입 기준보다 우선.
- 작업 전 [프런트엔드 구조 가이드](../../../docs/agents/frontend_structure.md)를 읽고 관련 구조·의존성·상태 관리·스타일링 기준 적용.

---

## 2. 작업 파이프라인

### 사전 단계. 기존 코드 및 기준 슬라이스 파악 (공통)

Phase 1과 Phase 2 중 어디로 진입하든 코드 작성 전에 반드시 먼저 수행한다.

1. **기존 코드·UI 파악:** 인접 `feature` 슬라이스, 라우트, 공용 UI 컴포넌트(`shared`)와 기존 테스트를 확인해 구조, 데이터 패칭 관례, 스타일링 패턴, 코드 밀도를 파악한다.
2. **작업 목록 초기화:** 파악한 구조를 바탕으로 전체 작업 단위를 분할해 최초 Todo 목록을 생성한다.

---

### Phase 1. 화면·상태 계약 및 정적 시안 (승인 게이트)

- 파악한 관례와 화면 목적·사용자 흐름을 기준으로 필요한 라우트, 레이아웃, 컴포넌트와 각 구성 요소의 책임·상태 소유권을 정한다.
- 필요한 범위에서 입력과 출력, URL 파라미터, API 계약, 로딩·빈 결과·오류 상태, 사용자 동작 및 접근성 요구를 정리한다.
- 프로젝트 구조와 의존성 경계를 존중해 타입·인터페이스와 컴포넌트 골격을 작성한다. 기존 계약이 불명확하면 확인된 사실과 가정을 구분한다.
- 화면 구성과 시각적 방향을 확인할 수 있도록 정적 시안을 작성한다. 필요한 경우 대표 상태와 예시 데이터를 표시한다.
- 정적 시안에서 실제 비즈니스 로직이나 API 연동은 구현하지 않는다. 예시 데이터와 미동작 요소는 시안 리뷰 시 명확히 알린다.
- 타입 검사와 import 경계를 확인한다. 이 단계에서는 테스트를 작성하지 않는다.
- 골격, 주요 계약과 정적 시안을 사용자에게 보고하고 리뷰를 요청한다. 승인 전 상세 구현에 진입하지 않는다.

---

### Phase 2. 상세 구현 및 자체 검증

#### 2-1. 화면·기능 구현

- 승인된 화면·상태 계약에 따라 화면, 상태 전이, 데이터 연동을 구현한다(Phase 1 생략 시 요청 범위 즉시 구현).
- 이미 승인된 계약은 재승인 없이 진행하되, 외부 API 계약이나 공유 타입 변경이 필요하면 영향과 대안을 먼저 제시하고 확인받는다.
- **구현 밀도 원칙:**
  - 서버 상태, 전역 UI 상태, URL 상태, 로컬 입력 상태의 소유권을 명확히 나누고 불필요한 파생 상태·중복 동기화를 만들지 않는다.
  - 외부 API 응답과 URL·폼 입력은 경계에서 한 번만 검증·변환하고, 내부 컴포넌트는 확정된 타입을 신뢰한다.
  - 기존 슬라이스(기준 코드)와 공용 UI 컴포넌트의 구조·밀도를 따른다.

#### 2-2. 테스트 및 화면 확인

- 변경 위험과 검증 가치에 따라 테스트를 선택하며, 사용자에게 중요한 동작과 실제 발생 가능한 로딩·빈 결과·실패 상황을 간결하게 검증한다.
- 테스트 추가·수정 시 [test-guide](../test-guide/SKILL.md)와 [프런트엔드 테스트 지침](../test-guide/references/frontend.md)을 적용하고, 타입 검사·린트·빌드 등 프로젝트 검증 명령을 실행한다.
- UI 변경은 가능한 환경에서 실제 화면을 확인하고, 확인하지 못한 화면이나 상태는 검증 결과에 명시한다.

#### 2-3. 자체 점검

구현 완료 후 변경 코드가 아래 기준을 충족하는지 확인하고, 어긋난 부분이 있으면 즉시 단순화한다.

1. 각 화면과 컴포넌트가 맡은 책임과 상태 소유권을 지키며 불필요한 상태 복제가 없는가?
2. 라우트·feature·shared 사이의 의존성이 프로젝트 경계를 지키는가?
3. 외부 데이터와 사용자 입력을 경계에서 검증·변환하고 내부 중복 방어를 배제했는가?
4. 로딩·빈 결과·오류 상태, 사용자 동작 및 기본 접근성(시맨틱 마크업·키보드 조작)이 계약에 맞게 처리되는가?

---

### Phase 3. 코드 리뷰 (위임 게이트)

- **실행 조건:** 사용자가 리뷰를 요청한 경우에만 [fe-review](../fe-review/SKILL.md) 스킬 적용(건너뛰기 요청 시 생략). 구현자 자체 점검은 Phase 2 완료 근거로만 사용.
- **위임 규칙:** 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차) 사용(모델 키: `review`). 첫 메시지에 `$fe-review` 적용, 변경 목적, 화면·상태 계약, 비교 기준과 검토 대상을 전달하며 리뷰 중 검토 대상 수정 금지.
- **예외 처리:** 모델 설정이 유효하지 않거나 위임 또는 결과 확인이 불가능하면 사유를 보고하고 리뷰를 미완료 상태로 유지.
- **결과 확인 및 종료:**
  - 서브에이전트로부터 [fe-review 출력 양식](../fe-review/SKILL.md#출력-양식)에 따른 보고를 받아 검토 범위와 근거를 확인한 뒤 사용자에게 전달.
  - 결함이나 정적 검사 실패를 근거와 함께 보고했다면 리뷰 결과로 처리. `수정 필요` 판정도 결과 확인 후 터미널 정리.
  - 범위 확인이나 권한 승인 등 사용자 개입 후 이어갈 작업이 있으면 터미널 유지.

---

### Phase 4. 커밋 (위임 게이트)

- **실행 조건:** 사용자가 커밋을 요청한 경우에만 [commit](../commit/SKILL.md) 스킬 적용.
- **범위 정리 및 위임:** 작업 목적, 포함·제외할 변경, 기존 staged 변경 처리 범위를 정리. 범위를 명확히 전달할 수 있으면 같은 작업 트리에서 [공통 Herdr 위임 절차](#3-공통-herdr-위임-절차)로 위임(모델 키: `commit`, 첫 메시지에 `$commit` 적용과 실제 커밋 요청 전달).
- **직접 처리 및 제약:** 같은 파일의 변경이 섞여 범위 전달이 어렵거나, 모델 설정이 유효하지 않거나, 위임을 시작할 수 없으면 구현 에이전트가 직접 처리. 위임 중에는 같은 Git 인덱스에 쓰기 금지.
- **결과 확인 및 종료:** 커밋 해시·메시지·남은 변경을 전달받고 Git에서 확인한 뒤 사용자에게 보고하고 터미널 정리. 범위 질문이나 권한·검증 실패로 중단되면 터미널을 유지하고 사유 전달.

---

## 3. 공통 Herdr 위임 절차

1. **모델 설정:** 작업 트리의 [모델 매핑 기준](../../rules/models.mdc)에서 해당 키(`review` / `commit`)의 `model`과 `reasoning_effort`를 읽어 `delegate_model`, `delegate_effort`에 설정.
2. **백그라운드 실행:** 부모의 `HC_TERMINAL_ID`를 첫 프롬프트에 전달하고, 완료 시 최종 결과(리뷰 양식 또는 커밋 해시·메시지)를 `hc send <부모 주소>` 본문에 직접 담아 보고하며 중단 시에만 사유를 전달하도록 지시. 고유한 터미널 이름과 작업 트리 루트를 지정하고 호출자 셸의 `PATH`를 전달해 Codex 실행:
   ```sh
   hc run --bg --name "$delegate_agent" --cwd "$worktree_root" -- \
     /usr/bin/env "PATH=$PATH" codex --no-daemon --model "$delegate_model" \
       --config "model_reasoning_effort=\"$delegate_effort\"" "$delegate_task"
   hc wait --timeout 30 "$delegate_agent"
   ```

3. **상태 확인:** 시작 직후 대기 상태나 시간 초과만으로 완료 판단 금지. 보고가 없고 상태가 불명확하면 `hc get`이나 필요한 범위의 `hc read`로 확인. 시간 초과 후에도 작업 중이면 같은 터미널을 대상으로 `hc wait` 재실행. 완료·중단 보고를 받거나 사용자 개입이 필요해지면 해당 단계의 처리 기준 적용. 실행 여부나 결과가 불명확한 동안 동일 작업 재실행 금지.
4. **터미널 정리:** 각 단계 기준에 따라 결과 확인 후 `hc kill`과 `hc rm`으로 터미널 정리. 사용자 개입 대기 시 터미널을 유지하고 필요한 조치 전달.

## 4. 작업 상태 및 출력 규약

### 4-1. Todo 목록 유지 및 갱신 규칙

* **최초 생성:** 사전 단계(기존 코드·UI 파악) 직후 전체 작업 단위를 분할해 최초 목록 생성.
* **순서 고정:** 최초 항목의 이름과 순서 유지. 진행 순서 변경이나 새 요구사항 추가 시에도 기존 항목 순서 변경 금지.
* **요구사항 반영:** 요구사항 변경 시 관련 항목을 즉시 갱신하거나 필요한 항목 추가.
* **항목 변경 제한:** 병합·분할·삭제는 요구사항 변경으로 기존 구성이 맞지 않거나 중복되어 진행 상태를 표현할 수 없는 경우에만 수행하며 변경 사유 짧게 명시.
* **재진행 처리:** 완료된 항목도 추가 요청·재검증 필요 시 미완료로 되돌리고 `재진행 중` 표시 후 재완료 시 최신 근거로 갱신.
* **생명주기:** 후속 요청이 기존 작업의 연속이면 새 목록으로 교체하지 않고 전체 작업 종료 시까지 유지.

### 4-2. 상시 출력 포맷 (매 턴 최하단 고정)

개발 진행 중 모든 응답의 최하단에 전체 Todo 목록과 완료 근거 유지·출력. Phase 1 생략 또는 리뷰·커밋 생략 시 사유 표시. 모든 개별 항목 완료 후에도 `작업 완료` 자동 체크 금지(`완료 확인 대기` 유지).

---

```text
📌 작업 목록
* [ ] 화면·상태 계약 및 정적 시안 — Phase 1
* [ ] 상세 구현 및 검증 — Phase 2
* [ ] 책임·경계 자체 점검 — Phase 2
* [ ] 코드 리뷰 — Phase 3
* [ ] 커밋 — Phase 4
* [ ] 작업 완료 *(완료 확인 대기)*

```

### 4-3. 보고 및 종료 프로토콜

사용자 요청 유형에 따른 상태 전이 및 출력 양식 적용:

| 사용자 요청 | 상태 처리 및 개발 모드 여부 |
| --- | --- |
| **완료 보고 요청** | 현재 결과와 미완료 항목만 보고. **`작업 완료` 체크 및 모드 종료 금지** |
| **작업 완료 선언 / 승인** | 최종 결과 보고 후 **`작업 완료` 체크 및 개발 모드 종료** |
| **작업 종료(중단) 선언** | 미완료 항목과 중단 사유 기록 후 **`작업 완료`(종료 의미) 체크 및 개발 모드 종료** |

**보고/종료 시 출력 템플릿:**

```text
✅ 작업 요약
   * 구현 목적, 핵심 변경 사항과 검증 결과
   * 주요 설계·로직 결정 사항
📌 작업 목록
   * [x] 완료 항목 — 근거
   * [ ] 미완료 항목 — 현재 상태와 사유

```
