# 테스트 작성 가이드

## 작업 대상별 참조

- Rust 테스트는 [Rust 테스트 지침](references/rust.md)을 읽고 적용.
- 프런트엔드 테스트는 [프런트엔드 테스트 지침](references/frontend.md)을 읽고 적용.
- 양쪽 테스트를 추가·수정할 때는 두 지침을 모두 읽고, 각 테스트에 해당하는 지침을 적용.

## 검증 목적별 분류

- `contract`: 사용자나 호출자에게 보장하기로 한 정상 동작과 오류 조건. 근거는 요구사항, API 문서, 화면 계약, 합의된 동작에서 확인. 보장 범위에 포함된 입력 제약이나 경계값도 여기에 분류.
- `edge`: 계약에 별도로 명시되지 않은 입력 방어, 경계값 처리, 의존성 실패 대응 등 구현상의 예외 상황.
- `regression`: 실제 버그의 재현 조건. 기존 계약 테스트가 동일한 실패를 잡으면 해당 테스트에 이슈를 연결하고, 별도 재현 조건이 있을 때 회귀 테스트를 추가.

## 작성 기준

- 1 테스트 1 시나리오: 하나의 테스트 함수에 여러 도메인 시나리오를 이어 붙이지 않고, 검증하려는 단일 동작과 기대 결과 단위로 함수를 분리한다.
- 프레임워크·표준 동작 테스트 금지: 잘못된 JSON 문법 파싱(400), 미지원 HTTP 메서드(405), 미등록 경로(404), 단순 값 전달, 언어·표준 라이브러리가 보장하는 동작은 테스트하지 않는다.
- 필요할 것 같은 추측성 테스트 지양: 요구사항·계약의 핵심 동작과 실제 발생 가능한 실패·보안 경계만 검증하며, 인공적인 문자열 변형·퍼징성 케이스를 만들지 않는다.
- 테스트를 추가하기 전 기존 테스트와 `test_support` 헬퍼를 먼저 확인하고, DB·서버 초기화 보일러플레이트를 테스트 본문에 중복 작성하지 않는다.
- 테스트 이름은 검증하는 동작과 기대 결과를 명확하게 드러내도록 작성한다.
- 준비 작업(Setup)은 테스트 의도를 가리지 않는 범위에서만 공통 함수로 분리하며, 결과에 영향을 주는 핵심 값은 테스트 본문에서 직접 확인 가능하게 둔다.
- 검증(Assert) 단계 직전에 구체적인 상태 변화나 반환값을 기대 결과 주석으로 작성한다.
- Mock·Fake 등 테스트 대역은 외부 의존성의 비용이나 실패 상황 재현 필요에 따라 제한적으로 사용하며, 최종 상태와 계약을 우선 검증한다.
- 단순 값 전달, 내부 구현을 그대로 반복하는 검증, 언어·표준 라이브러리가 보장하는 동작은 테스트 지양
- 추가·수정한 테스트를 프로젝트의 검증 명령으로 실행하고 결과 확인
