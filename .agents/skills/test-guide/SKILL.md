# 테스트 작성 가이드

## 테스트 모듈과 변경 승인

Rust 소스 파일 안에 테스트를 추가하거나 변경할 때 `#[cfg(test)] mod tests` 아래에 검증 목적에 맞는 하위 모듈을 둔다. 해당 테스트가 있는 하위 모듈만 선언한다.

- `mod contract`에는 호출자에게 보장하기로 한 정상 동작과 오류 조건을 검증하는 테스트를 둔다. 근거는 요구사항, API 문서, 합의된 동작에서 확인한다. 호출자에게 보장한 입력 제약, 경계값, 오류 응답도 포함한다.
- `mod edge`에는 구현상의 입력 방어, 경계값 처리, 의존성 실패 대응을 검증하는 테스트를 둔다. 에이전트가 추가·수정·삭제할 수 있다.
- `mod regression`에는 실제 버그의 재현 조건을 검증하는 테스트를 둔다. 요청받은 버그의 재현 테스트는 에이전트가 추가할 수 있다. 기존 계약 테스트가 동일한 실패를 잡으면 해당 테스트에 이슈를 연결하고, 별도 재현 조건이 있을 때 회귀 테스트를 추가한다.

경계값은 호출자에게 보장하는 범위를 기준으로 분류한다. 예를 들어 API가 양의 정수 밀리초 TTL을 요구하면 `1ms` 미만 입력 거절은 `contract`에 둔다. 저장소의 표현 한계에서 정해진 TTL 상한은 `edge`에 두고, API가 그 상한을 보장하면 `contract`에 둔다.

기존 계약 테스트와 수정이 완료된 버그의 회귀 테스트는 기대 동작을 바꾸거나 검증을 약화·제거하기 전에 사용자 승인을 받는다. 이 기준은 테스트 비활성화, 모듈 이동, 공용 헬퍼 변경으로 검증 범위가 줄어들 때도 적용한다. 검증 조건과 기대 결과를 그대로 유지하는 이름·구조 변경은 자율적으로 진행할 수 있다. 사용자가 기대 동작의 변경을 명시적으로 요청하면 해당 범위의 테스트 변경도 승인된 것으로 본다.

## 작성 기준

- 요구사항이나 계약 중 실패 시 문제가 되는 동작을 검증(필요할 '것' 같은 추측성 테스트 지양)
- 테스트를 추가하기 전 기존 테스트를 먼저 확인하고, 발견하려는 오류와 기존 테스트로 잡을 수 없는 이유를 분명히 한 뒤 작성
- 테스트 이름은 검증하는 동작과 기대 결과를 명확하게 드러내도록 작성
- 준비 작업(Setup)은 테스트 의도를 가리지 않는 범위에서만 공통 함수로 분리
- 테스트 데이터는 결과를 재현할 수 있도록 선택하고, 결과에 영향을 주는 핵심 값은 테스트 본문 안에서 직접 확인 가능하게 작성
- 검증(Assert) 단계 직전에 구체적인 상태 변화나 반환값을 기대 결과 주석으로 작성
- Mock·Fake 등 테스트 대역은 외부 의존성의 비용이나 실패 상황 재현 필요에 따라 제한적으로 사용. 최종 상태와 계약을 우선 검증하고, 호출 횟수·순서는 요구사항이나 계약에 포함된 경우에만 검증.
- 단순 값 전달, 내부 구현을 그대로 반복하는 검증, 언어·표준 라이브러리가 보장하는 동작은 테스트 지양
- 추가·수정한 테스트를 프로젝트의 검증 명령으로 실행하고 결과 확인
