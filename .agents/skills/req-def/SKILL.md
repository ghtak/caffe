# req-def

모호하거나 이해관계·정책·예외가 얽힌 요구를 단계적 질의와 근거 탐색으로 구체화하여, 자율 에이전트 및 후속 설계(`macro-spec`, `rust-impl`, `fe-impl`)가 멈추지 않고 실행·검증할 수 있는 기준 문서를 작성한다.

## 사용 시점 및 경계

- 사용 (`req-def`): 요구 범위나 정책이 불명확해 단계적 인터뷰가 필요한 경우, 여러 시스템·권한 경계의 책임 주체를 가려야 하는 경우, 자율 실행 중 에이전트가 멈춰서 사용자에게 물어야 할 조건(`사용자 문의 기준`)과 위임 범위를 사전 확정해야 하는 경우.
- 미사용 (`req-seed` 위임): 기능 목적과 시나리오가 이미 명확하여 질문 없이 즉시 상위 레벨 요구사항 초안만 뽑아 `macro-spec`으로 넘기면 되는 경우.

## 진행 원칙

- 기본 진행: 사용자 요청, 관련 코드·테스트와 문서에서 결정 근거를 먼저 찾는다. 기존 근거로 결정할 수 있거나 영향이 작고 되돌릴 수 있는 선택은 가정을 기록하고 진행한다.
- 단계적 질의: 사용자 문의 기준에 해당하면 핵심 모호성을 해소할 질문을 한 번에 1~2개씩만 제시하고, 답변을 바탕으로 다음 질문을 정한다. 질의 진행 중에는 아래 출력 양식을 미리 작성하지 않는다.
- 출력 시점: 후속 작업의 실행·검증 기준이 마련되었거나 사용자가 정리를 요청할 때 문서로 정리한다. 사용자 결정이 남아 있으면 관련 요건과 진행 가능 범위를 표시한다.
- 결정 상태: 사용자가 정한 사항, 근거에 따라 채택한 가정, 제안, 사용자 결정이 남은 사항을 구분한다.
- 설계와의 경계: 사용자에게 보이는 동작·시스템의 책임·충족 조건을 정의한다. 명시된 기술 제약은 반영하되, 내부 모듈 구조·DB/Redis 스키마·API DTO·테스트 도구 등 구체적인 설계 및 구현 방식은 후속 `macro-spec` 및 구현 단계에서 결정한다.

## 1. 목적·전략·목표·완료 조건

- 목적 - 해결할 문제와 작업이 필요한 이유. 확인된 배경과 원인을 바탕으로 범위를 정한다.
- 전략 - 목적을 달성하기 위한 접근과 우선순위. 후속 작업의 판단에 필요한 진행 순서, 주요 의존 관계, 위임 범위를 해당하는 만큼 명시한다.
- 목표 - 작업이 만들어야 하는 구체적인 결과물이나 상태와 그 적용 범위.
- 완료 조건 - 전체 작업의 종료를 판단할 관찰 가능한 결과와 확인 방법. 필수 결과물과 검증 범위, 남은 사항이 완료를 막는 조건을 명시한다. 세부 합격 기준은 해당 요건의 검증 조건에 연결한다.

## 2. 요건의 정의 (Requirements)

- 요구 충족을 위한 필수 조건 도출.
- 사용 주체와 판단·처리·결과 제공을 담당하는 책임 주체 구분.
- 사용자 행동 또는 발생 계기 -> 책임 주체의 행동 또는 반응 -> 관찰 가능한 결과 순서로 시나리오 정의.
- 요건마다 관련 시나리오·제약 및 예외·합격 기준을 함께 정리하여, 어떤 조건으로 해당 요건의 충족 여부를 판단하는지 연결.

## 3. 사용자 문의 기준

요건을 정의할 때 이 기준을 적용하고, 후속 작업자(자율 에이전트 포함)가 만날 수 있는 구체적 조건을 `상세 > 사용자 문의 기준`에 기록한다.

- 문의 - 기존 근거로 선택할 수 없고 선택에 따라 목적·범위·사용자에게 보이는 계약·완료 조건이 실질적으로 달라질 때, 범위 확대나 비가역적 조치에 필요한 결정·승인이 아직 없을 때, 필수 입력이나 권한을 사용자만 제공할 수 있을 때 문의한다.
- 자동 진행 - 기존 규칙으로 판단 가능하거나 위임된 범위에서 되돌릴 수 있는 세부 선택은 진행한다. 판단에 사용한 가정과 결과에 영향을 주는 선택을 결과에 남긴다. 통상적인 진행과 검증 결과는 최종 결과에 모아 전달한다.
- 문의 방식 - 결정마다 질문과 필요한 배경, 선택에 따른 결과, 답변 전 진행할 수 있는 범위를 제시한다. 해당 결정에 의존하는 작업은 답변을 기다리고 독립적으로 진행 가능한 작업은 이어간다.

## 출력 양식

아래 양식으로 정리한다. 요건별 상세는 필요한 만큼 반복한다. 작업별 문의 조건이 없다면 위임된 범위와 최종 결과로 전달할 사항을 한 줄로 정리한다. 가정·미결정 사항이 없으면 해당 절을 생략한다.

```markdown
# 목적
해결할 문제와 작업이 필요한 이유. 관련 배경과 확인된 원인.

# 전략
목표 달성을 위한 접근, 우선순위, 주요 의존 관계와 위임 범위.

# 목표
기대하는 결과물 또는 상태와 적용 범위.

# 완료 조건
전체 작업의 완료를 판단할 관찰 가능한 기준, 확인 방법과 필요한 검증 범위.

# 상세
## 요건 - {요건 제목}
- 동작과 조건: 무엇을 제공하고 어떤 조건을 충족해야 하는지 명시.
- 결정 상태: 사용자 결정·채택한 가정·제안·미결정 구분.
- 사용 주체: 기능을 실행하거나 영향을 받는 액터(사용자, 시스템, 외부 모듈 등).
- 책임 주체: 판단·처리·결과 제공의 담당 주체와 책임 범위.
- 시나리오: 사용자 행동 또는 발생 계기 -> 담당 시스템의 반응 -> 관찰 가능한 결과. 정상 흐름 및 주요 분기 포함.
- 제약 및 예외: 반드시 지켜야 할 한계 조건 및 제외 범위(Out of Scope).
- 검증 조건: 이 요건을 확인할 상황·입력, 관찰 가능한 기대 결과 및 합격 기준.

## 사용자 문의 기준

- 문의 조건 - {관련 요건과 실제로 문의해야 하는 상황}
- 필요한 결정 - {사용자에게 필요한 답변·입력·승인과 선택별 영향}
- 답변 전 진행 범위 - {답을 기다려야 할 작업과 계속할 수 있는 작업}
- 자동 진행 범위 - {위임된 판단, 적용할 기본값 또는 가정, 최종 결과에 남길 사항}

# 가정·미결정 사항
- 관련 요건, 확인할 가정이나 남은 질문, 결정되지 않았을 때의 영향과 다음 작업 진행 가능 여부.
```
