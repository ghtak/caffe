# 프런트엔드 코드 리뷰

변경 코드가 요구사항과 화면·데이터 계약을 충족하고 기존 책임 배치, 계층 역할, 의존 경계를 일관되게 따르는지 검토한다. 품질 점수·변경 리스크·발견 사항을 근거와 함께 정리한다.

리뷰는 읽기 전용으로 수행한다. 코드·테스트·설정 등 사용자 파일은 직접 수정하지 않고 수정 방향만 제시한다. 검사에 필요한 빌드 산출물과 캐시는 허용한다.

## 진행 절차

1. **컨텍스트 확인:** 비교 기준(Base)과 대상 커밋, 변경 목적·화면 계약, 영향받는 사용자 흐름·호출자·데이터 흐름을 파악한다. [프런트엔드 구조 가이드](../../../docs/agents/frontend_structure.md)와 관련 기존 코드·테스트를 확인한다. 비교 기준과 대상 커밋, Node.js·패키지 매니저 버전, 실행 플랫폼과 확인한 브라우저·화면 크기를 기록한다.
2. **정적 검사:** `just conbira-ui-lint`, `just conbira-ui-check`, `just conbira-ui-build`를 순서대로 실행한다. 프로젝트에 별도 포맷 검사 명령이 있으면 함께 실행한다. 실패하면 결과와 수정 방향을 보고하고 리뷰 중단. 실행하지 않은 검사와 품질 점수·리스크는 `미평가`로 표시. 실행할 수 없는 명령은 사유와 미확인 범위를 기록하고 판정을 보류.
3. **테스트 및 화면 확인:** 변경과 관련된 자동 테스트를 실행하고 실패한 테스트의 이름·원인·영향과 수정 방향을 기록한다. 테스트 명령이 없으면 사유와 미확인 범위를 기록한다. UI 변경은 가능한 환경에서 정상·로딩·빈 결과·오류 등 해당되는 상태와 주요 사용자 흐름을 확인한다. 키보드 사용과 변경에 관련된 화면 크기도 확인한다. 실행하지 못한 테스트, 브라우저·화면 크기와 상태는 사유와 함께 기록한다.
4. **리스크 분류:** 복구 가능성(단방향/양방향)과 아키텍처 수준 구조 변경 여부를 평가한다.
5. **코드·테스트 평가:** 관련 코드와 테스트를 읽고 실행 결과를 확인해 7개 품질 항목을 평가한다. 아키텍처 일관성은 아래의 질문 제기 → 근거 확인 → 평가를 필요한 만큼 반복하여 검토한다. 확인하지 못한 내용은 추정으로 채우지 않는다.
6. **결과 정리:** 지정된 출력 양식에 따라 판정, 리스크, 품질 점수와 발견 사항을 정리한다.

## 품질 점수 (100점 환산)

각 항목을 `0~4점`으로 평가 후 정규화한다. 동일 근본 원인이 여러 항목에 영향을 주면 각 점수에는 반영하되 발견 사항은 중복 작성하지 않는다.

- **계산식:** `총점 = 100 × Σ(항목 점수 ÷ 4 × 배점) ÷ Σ(적용 항목 배점)`
- **N/A:** 변경과 무관한 항목은 사유를 적고 배점 합계에서 제외한다.
- **미확인:** 판단 근거가 부족하면 `N/A`나 `0점`으로 대체하지 않고 `미확인`으로 표기한다. 총점과 통과 판정은 보류한다.

| 항목 | 배점 | 주요 확인 내용 |
| --- | ---: | --- |
| 기능·사용자 흐름 | 20 | 요구사항·화면 계약, 사용자 동작, 정상·실패·경계 상태, 기존 동작 호환성 |
| 아키텍처 일관성 | 15 | 정책과 상태의 소유권, 화면·모듈 책임, 의존 방향과 데이터 접근 경계 |
| 가독성과 구조 | 10 | 식별자·제어 흐름의 명확성, 불필요한 파생 상태·1회용 훅·래퍼 및 중복 배제 |
| 안정성 | 15 | 로딩·오류 처리, 상태 일관성(불필요한 효과 동기화 배제), 중복 제출·요청 방지, 자원 정리 |
| 보안 | 15 | 인증·권한 경계, 입력·외부 데이터 처리, 민감정보 노출, 안전하지 않은 렌더링 |
| 접근성 | 15 | 의미 있는 마크업, 키보드 조작, 포커스, 이름·상태 전달, 변경 범위의 시각적 접근성 |
| 성능·테스트 용이성 | 10 | 불필요한 요청·렌더링, 큰 리소스, 사용자 동작 중심 검증과 구현 세부사항·합성 테스트 비대화 배제 |

- **점수 척도:** `4`(근거 확인 및 문제 없음) / `3`(주요 조건 충족, 사소한 개선) / `2`(동작·유지보수 보완 필요) / `1`(주요 조건 큰 결함) / `0`(핵심 계약 불성립)

### 아키텍처 일관성

1. **질문 제기** — 변경에서 내린 설계 선택을 짚고, 답에 따라 평가가 달라질 구체적인 질문을 세운다. 질문의 수와 깊이는 변경 영향에 맞춘다.
   - **관점** — 화면 정책, 서버 캐시, URL·폼·UI 상태의 소유자는 누구인가? 정책이 바뀌면 여러 화면이나 훅에서 같은 판단을 수정해야 하는가?
   - **계층** — 라우팅·기능 간 화면 조합·도메인 화면·데이터 접근이 각각 `app`, `features`, `shared` 내 적절한 위치에 있는가? UI가 데이터 접근 책임을 직접 떠맡는가?
   - **경계** — 의존 방향이 프런트엔드 구조 가이드에 맞는가? 기능 간 직접 의존이나 `shared`의 도메인 의존이 생겼는가? 라우트·컴포넌트·데이터 계약 변경은 어느 호출자와 사용자 흐름에 영향을 주는가?
2. **근거 확인** — 프런트엔드 구조 가이드와 같은 책임을 수행하는 기존 경로를 참고해 라우팅·렌더링·데이터 흐름, 공개 계약, import 관계와 테스트에서 답과 근거 위치를 찾는다. 기존 구현이 서로 다르면 책임을 소유하는 구현과 계약을 확인한다. 비교 대상이 없는 신규 경로는 연결되는 모듈의 계약과 의존 관계를 확인한다. 판단에 필요한 설계 의도가 확인되지 않으면 작성자에게 확인할 질문을 남긴다.
3. **평가** — 확인한 답을 변경 목적과 기존 책임 배치에 비추어 평가하고 화면·호출자·유지보수에 생기는 영향을 설명한다. 의도적인 구조 변경은 변경 목적, 새 책임 소유자, 영향받는 경로의 전환 범위와 계약 호환성을 근거로 평가한다. 이번 변경이 새로 만들거나 적용 범위를 넓힌 위반을 발견 사항에 포함한다. 평가에 필요한 근거가 부족하면 `미확인`으로 기록한다.

**후속 질문과 종료**

- 새로 확인한 책임·의존 관계나 반대 근거를 살핀다. 후속 질문의 답에 따라 평가, 영향 범위, 심각도 또는 수정 방향이 달라질 수 있으면 질문 제기로 돌아간다.
- **검토 완료** — 판단에 필요한 답을 근거로 확인했고, 변경의 영향 범위에서 결론을 바꿀 열린 질문이 없으면 해당 쟁점의 검토를 끝낸다. 결론의 근거와 확인 범위를 남긴다.
- **미확인** — 결론을 바꿀 질문에 답할 근거가 부족하면 남은 질문, 부족한 근거와 확인 방법을 기록하고 다른 쟁점의 검토를 이어간다.

평가에 영향을 준 최초·후속 질문의 연결, 답과 근거 위치, 평가와 영향, 종료 근거를 출력의 **아키텍처 일관성 검토**에 남긴다. 구조가 타당하다는 결론에 도달한 주요 질문도 포함한다. 관련 쟁점이 없거나 검토하지 못한 경우에는 사유를 한 줄로 기록한다.

### 코드 밀도 및 과잉 설계 점검

아래 항목에 해당하는 군더더기가 발견되면 영향 범위에 따라 `경미`(가독성·유지보수 저하) 또는 `주요`(상태 불일치·무한 루프·중복 요청) 발견 사항으로 기록하고 단순화 방향을 제시한다.

- **파생 상태 복제 및 불필요한 효과 동기화:** 서버 캐시(TanStack Query), URL 파라미터, 폼 상태에서 렌더링 중 직접 계산 가능한 값을 `useState`와 `useEffect`로 복제·동기화하는 코드.
- **불필요한 중간 추상화:** 재사용 근거 없는 단일 화면용 커스텀 훅 분리, props를 그대로 전달하는 1:1 래퍼 컴포넌트, 이미 경계에서 검증된 타입에 대한 내부 컴포넌트 중복 방어.
- **비동기 상호작용 경합 누락:** 버튼 연타·이중 제출 방지가 없거나, 인증 토큰·일회성 인가 상태를 불필요하게 브라우저 영구 저장소(`localStorage`)에 남기는 처리.
- **구현 세부사항·합성 테스트 비대화:** 사용자 동작과 화면 계약이 아닌 내부 훅 호출 횟수·스타일 클래스명·라우터 기본 동작을 검증하거나, 여러 독립 시나리오를 하나의 거대 테스트 함수에 몰아넣은 경우.

## 변경 리스크

### 1. 복구 가능성

프런트엔드 코드 복원뿐 아니라 배포 후 변경된 서버 데이터, 브라우저 저장 데이터와 외부 시스템 효과까지 포함해 판단한다.

- **양방향 (PR 롤백 가능):** 이전 코드 재배포만으로 데이터 보정이나 외부 조치 없이 기존 동작으로 복귀 가능.
- **단방향 (PR 롤백 불가):** 데이터 변환·삭제, 외부 발송·결제 등으로 별도 복원·보정 절차 필요.
- **미확인:** 배포 호환성이나 영향받는 상태를 확인하지 못함.

### 2. 아키텍처 수준 구조 변경

단순 파일 이동·이름 변경이 아닌 **화면·모듈 책임, 의존 방향, 상태·데이터 소유권, 라우팅·공개 UI 계약, 배포 단위 또는 동기·비동기 처리 방식**의 실질적 변화 여부를 확인한다.

구조 변경 여부와 복구 가능성은 리스크 등급에 반영한다. 경계 위반의 심각도는 영향받는 경로와 책임을 근거로 판정한다.

### 3. 리스크 등급 판정

- **높음:** 단방향 변경(PR 롤백 불가).
- **중간:** 양방향 변경이나 아키텍처 수준 구조 변경 포함. 호출자·계약 호환성 추가 검증 필요.
- **낮음:** 양방향 변경이며 아키텍처 수준 구조 변경 없음.
- **미확인:** 복구 가능성 또는 아키텍처 영향의 근거 부족.

## 발견 사항 및 최종 판정

### 발견 사항 작성 규칙

- 모든 항목에 **위치, 발생 조건, 실제/예상 영향, 코드·실행 근거, 수정 방향**을 명시한다.
- 아키텍처 일관성 발견 사항에는 기존 책임 또는 경계의 근거 위치, 위반 지점, 영향받는 화면·호출 경로와 책임을 둘 위치를 기록한다.
- 재현하지 못한 문제는 추론 근거와 확인 방법을 적는다. 단순 취향·가정 기반 개선 제안은 결함과 분리한다.
- **심각도:**
  - `치명`: 데이터 손실, 권한 우회, 광범위한 장애. 총점과 무관하게 수정 필요.
  - `주요`: 요구사항·화면 계약 위반, 핵심 사용자 흐름 또는 접근성 실패, 근거가 확인된 책임 중복·계층 우회·경계 위반의 신규 발생 또는 확산. 총점과 무관하게 수정 필요.
  - `경미`: 영향이 제한적인 UI·가독성·구조 문제, 파생 상태 복제·1회용 훅 분리·구현 세부사항 테스트 비대화 등 과잉 설계 단순화. 영향과 우선순위 기록.

### 최종 판정 순서

1. **수정 필요:** `치명`·`주요` 발견 사항, 적용 항목 중 `2점 이하`, 총점 `80점 미만`, 정적 검사 실패 또는 코드 결함에 의한 테스트 실패 시. 원인과 수정 방향 제시.
2. **판정 보류:** 수정 필요 사유는 없으나 실패 원인이 환경 문제인지 코드 결함인지 확인되지 않거나, `미확인` 항목이 있거나 리스크 등급 판정의 필수 근거가 부족할 때.
3. **통과:** 모든 적용 항목이 `3점 이상`, `총점 80점 이상`, 리스크 확인 완료 시. 아키텍처 일관성은 적용 여부와 판단 근거를 명시한다. 검토한 변경 범위에 대한 판단이며 전체 배포 승인을 의미하지 않는다.

## 출력 양식

